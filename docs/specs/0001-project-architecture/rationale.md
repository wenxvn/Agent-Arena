# 项目技术架构依据

## Context

Agent Arena 是个人开发的本地实验项目，目标是学习 Agent Loop，并比较不同 Agent 策略在确定性、部分可观测世界中的表现。当前仓库没有业务源代码，因此架构需要优先解决可运行、可重复、可测试和可展示的问题，而不是解决尚不存在的并发、部署和多租户问题。

## Options considered

### 选项一，Python 本地分层单体

优点是与项目学习目标一致，调试路径短，部署成本最低，同时可以通过包和接口保持边界。缺点是暂时不能直接提供在线访问，也不能天然支持并发实验。

### 选项二，带 Web API 和数据库的服务

优点是更容易扩展远程调用、历史查询和多人访问。缺点是会提前引入服务部署、认证、数据库迁移、并发状态和运维问题，掩盖 Agent 实验本身的学习目标。

### 选项三，使用通用 Agent 框架作为核心

优点是可以较快获得工具调用、记忆或编排能力。缺点是关键循环会被框架抽象隐藏，难以清楚观察 Action、Observation、错误处理和评估边界，也会增加版本和依赖负担。

### 选项四，测试和 CI 直接调用真实模型

优点是能更早暴露供应商协议差异。缺点是受网络、配额、价格、模型变更和非确定输出影响，无法提供稳定的回归信号。

## Rationale

选择本地分层单体，是因为用户规模为零到很小，项目的第一价值是理解 Agent 的可观察行为。Python 和 Pydantic 让数据契约清楚，uv 和锁文件让环境可复现。OpenAI SDK 加独立适配层复用百炼协议，同时避免供应商细节渗透到 Agent 和 Environment。`DecisionProvider` 注入点和可编程 Fake 队列让测试可以控制每次决策，不会意外调用真实模型。确定性世界和 JSON Trace 共同保证规则测试和 benchmark 有稳定基础。

选择 CLI 优先，是因为第一版需要一个真正可运行和可展示的项目，但用户已经确认图形界面延后。保留 `ui/` 边界可以在 Release 3 增加 Streamlit，而不改变核心循环。

选择版本化 prompt、world JSON 和 seed，是因为实验结果必须能追溯到具体输入。配置加载顺序和 CLI 的 Fake 默认值避免了本地演示或 CI 意外消耗真实模型额度。选择关闭 reasoning，是因为项目需要可审计的短决策说明，而不是保存模型的完整内部推理内容。

## Tradeoffs

本方案牺牲了线上可访问性、数据库查询能力和即时图形展示。它也要求实现者自己把 Agent Loop、校验、重试、脱敏和 Trace 组合起来。Python 3.13 需要依赖兼容性纪律，Pydantic 也不能代替 Environment 对世界规则的校验。若未来出现多人访问、长期实验历史或高并发 benchmark，这个架构需要增加持久化和服务边界，但当前没有证据支持提前承担这些成本。
