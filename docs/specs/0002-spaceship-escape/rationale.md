# Spaceship Escape 环境依据

## Context

项目需要一个可由人通过公开工具完成的世界，用来区分环境规则错误与 Agent 决策错误。世界必须部分可观测、确定且可重置，Agent 不能读取完整世界状态。第一版只需要一个小而完整的任务，不需要通用谜题引擎、数据库或外部服务。

世界需要同时支持规则测试和后续受步数限制的 Agent Loop。若地图、物品状态和工具行为不精确，benchmark 结果将无法解释。已有架构已确定 Pydantic 数据契约、版本化世界配置、Fake provider 和 Environment 与 Agent 的隔离边界。

## Options considered

### 选项一，全部 Python 硬编码

房间、对象和规则全部写在一个 Python 模块中。

**优点**:

1. 初始实现最快。

**缺点**:

1. 世界版本和静态内容不易审阅或复用。

### 选项二，静态 JSON 加内存状态加 Python 规则

JSON 保存地图和静态内容，Pydantic 模型保存每局状态，Python 集中执行条件和转换。

**优点**:

1. 静态事实可审阅和版本化，复杂条件仍保持直接可测试。

**缺点**:

1. 实现者需要维护 JSON 模型与 Python 规则之间的一致性。

### 选项三，完全配置化规则引擎

把所有条件和状态效果编码为通用 JSON 规则。

**优点**:

1. 未来新世界可复用更多配置。

**缺点**:

1. 第一版会先建设抽象层，而不是交付可运行环境，调试成本更高。

## Rationale

选择选项二。它保留版本化世界配置和确定性 reset，同时让 reactor 和授权码这类条件规则保持清楚。相对全部 Python 硬编码，它更容易追溯每局使用的世界版本。相对通用规则引擎，它不会把首个小世界变成框架工程。

用户确认了无 access card 的单主线路径、Storage Room 的两个物品、独立供电的 diagnostic terminal 和固定授权码。这样可以让规则测试覆盖探索、依赖、失败反馈和恢复，又不增加第二条门禁依赖。
