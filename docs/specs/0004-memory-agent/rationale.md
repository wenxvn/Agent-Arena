# MemoryAgent 理由

## 背景

Release 1 已有确定性世界、严格 Action schema、受限 Runner 和安全 JSON episode trace。真实模型冒烟验证证明动作格式不再阻塞基线，但 Agent 仍会重复无效探索。Release 2 需要一个可解释的变化，并能与该基线对比。

Agent 只能通过 Observation 和 ToolResult 学习。传递完整历史会模糊实验并导致 prompt 持续增长。再调用模型总结会增加第二个变化组件。因此设计必须用确定性 Python 规则保留有用公开信息。

## 备选方案

### 方案一：规则驱动的结构化记忆

从公开输入维护有类型字段，在每个已执行 Action 后更新，并按固定顺序渲染。

**优点**：

1. 唯一有意改变的实验变量是 Agent 架构。
2. 单元测试能证明更新行为和信息边界。
3. 不增加 provider 成本、密钥或原始响应暴露面。

**缺点**：

1. 初期问题映射与当前 ToolReason 集合相关。
2. 规则可能遗漏未来基于模型的提取器能捕获的信息。

### 方案二：完整对话历史

每次 provider 请求都传递历史 Observation 和工具结果。

**优点**：

1. 几乎不需要提取逻辑。

**缺点**：

1. prompt 增长使长局面更难控制且成本更高。
2. 它不能研究结构化记忆或信息筛选。

### 方案三：模型驱动的记忆总结

额外发起 provider 请求，把近期经历总结为记忆。

**优点**：

1. 可以表达简单规则未覆盖的事实。

**缺点**：

1. 增加第二种模型行为、成本和失败模式。
2. Release 2 结果更难只归因于记忆。

## 理由

规则驱动的结构化记忆是最小且有价值的实验变化。现有公开数据契约提供全部输入，而 Runner 已经拥有已校验 Action 变成 Environment 结果的唯一位置。保持 reducer 为纯函数使规则可审查，并保护 Environment 边界。

当两个 Agent 使用相同基础指令和运行时配置时，对照才公平。MemoryAgent 必然增加公开上下文，因此 prompt 大小、token 用量和延迟是后续 benchmark 应记录的结果，不是应强行消除的配置差异。现在记录基础 prompt 哈希、运行来源和 provider 用量，为后续功能提供可验证证据。

即使 Environment 是确定的，记忆值也会成为 provider 输入。先脱敏再存储，并把它放入带标签的非指令 user message，可以防止公开结果成为 system 指令。两个 Agent 的基础 prompt 始终是唯一 system 指令。
