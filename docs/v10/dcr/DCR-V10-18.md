## 1. 原状与根因（V9 证据）

- 事实：V8 正式实例（seed 0）**没有风暴**，“风暴/噪声/生命窗”在评估里从未真实出现。
- 事实：0/2 → 2/2 的转变来自单条短路（补给规则公开后即可通关），构念中的“搜索—营救权衡”没有被测到。
- 根因：A 规则（无风暴窗口、无漏检）+ C 接口（救援不要求信号）。

## 2. V10 规则

1. **救援必须先有信号**：`rescue(area)` 只有在该区曾返回 `SIGNAL_FOUND` 时才执行，否则 `NO_SIGNAL_TO_RESCUE`——逐个盲救的路径被消除。
2. **风暴窗口公开、代价真实**：每个 seed 有 0–2 段风暴（公开时段）。风暴内 `search` 耗 3 tick 且漏检率 0.5–0.7；非风暴耗 1 tick、漏检率 0.05–0.1。漏检由 `sha256(seed|zone|attempt)` 决定，可复算、可重放。
3. **生命窗**：`life_window_end` 之前未救到即 `SURVIVOR_LOST`；误救（有信号但区域错）不存在，因为信号只会在真实区域出现。
4. 4 个预登记实例：seed 0 是**晴稳对照**（无风暴），1–3 分别有 1–2 段风暴，生还者、生命窗与漏检率都不同。

## 4. 对照结果（`python -m agent_arena.v10.baselines.suite MAP-11`）

| 策略 | 成功 | 搜索次数 | 风暴内搜索 | 说明 |
|---|---:|---|---:|---|
| Oracle | 4/4 | 1–3 | 0 | 机制触发 3/4（seed 0 是晴稳对照） |
| public_heuristic（风暴里等待） | 4/4 | 1–3 | 0 | 生命窗内完成 |
| blind_rescue（不搜索硬救，V9 旁路） | **0/4** | 0 | 0 | 全部 `NO_SIGNAL_TO_RESCUE` |
| storm_search（无视风暴） | 4/4 | 1–3 | 1–3 | 合法但把风险与时间都押上 |
| single_search_giveup（只搜一次） | 2/4 | 1 | 0 | 只在生还者恰在首个搜索区时成功 |
| waste_window（开局空转 6 tick） | 2/4 | 1–3 | 0 | 生命窗被浪费 |
| legal_random（4 seed × 20） | 0/80 | — | — | — |

要点：V9 的“无风暴实例 + 救援不要求信号”两个缺口同时补上——`blind_rescue` 0/4；风暴感知策略 `storm_searches = 0`，而无视风暴的策略虽然也能成功，但把每一局都变成“高漏检 + 慢搜索”。
