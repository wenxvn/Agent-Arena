## 1. 原状与根因（V9 证据）

- 事实：阈值公开后 MiMo 的失败从“短路”转成缺氧，`skip_pump` 仍能成功——说明泵/封舱的因果链没有被成功条件约束住。
- 根因：C 成功判据只要求修复，不要求维持水位与供氧；A 规则里三条链没有同时收口。

## 2. V10 规则

1. **修复有双重前提**：`repair` 要求 `水位 ≤ repair_water_limit` **且** `供氧 ≥ repair_oxygen_min`，否则分别返回 `TOO_MUCH_WATER` / `OXYGEN_TOO_LOW`。
2. **三链同时结算**：每 tick 漏水 `+当前漏速`、电力 `-1`、供氧 `-1`；`pump`（水位 −4、电力 −2）、`seal`（本 tick 停漏、供氧 −2）、`vent`（供氧 +3、水位 +1）。
3. **漏速随时间上升**：每 `surge_every` tick 漏速 +1，逼迫在电力与供氧之间取舍。
4. **任一维度归零即失败**：水位 > 8 → `FLOODED`；电力 ≤ 0 → `LOST_POWER`；供氧 ≤ 0 → `LOST_OXYGEN`。
5. 4 个预登记实例：初始水位/电力/供氧、漏速、激增周期与修复门槛都不同。

## 4. 对照结果（`python -m agent_arena.v10.baselines.suite MAP-09`）

| 策略 | 成功 | 说明 |
|---|---:|---|
| Oracle（真值 BFS） | 4/4 | 计划长度 2–5，机制触发 4/4 |
| public_heuristic（先补氧、再降水、后修复） | 4/4 | 全程水位/供氧/电力均 > 0 |
| skip_pump（只通风） | **0/4** | 全部 `FLOODED` |
| skip_vent（只开泵） | **1/4** | 3 个实例 `LOST_POWER`，1 个侥幸完成 |
| seal_only（只封舱） | **0/4** | 全部 `LOST_OXYGEN` |
| legal_random（4 seed × 20） | 0/80 | — |

要点：三条链**各自都是必要的**——去掉泵会淹、去掉通风会把电力耗光（或在供氧门槛前卡住）、只封舱会缺氧。这是 V9 的“`skip_pump` 仍成功”在 V10 被消除的直接证据。
