# DCR-V10-38：MAP-20 公开规则补充“时间只在 wait 时推进”

- 状态：`accepted_by_agent`（`agent_reviewed`）
- 类型：**公开信息补全**（不改规则逻辑、不改预算、不改成功条件、不改指标）
- 关联：`DCR-V10-24/25/28`（同一类“公开契约不完整”）、`trigger-gap-analysis.md`、`final-report.md` §10.1
- 代码：`v10/runtime/map20.py`（`public_rules()`）
- 真实模型：阶段 13（`ledger_v10_019.jsonl`），3 局

## 1. 问题

MAP-20 的三局（阶段 4，`-j2`）都是 **56/56 决策全部为 `set_flow [25,25,10]`**，
`tick` 始终为 0、产能 0。动作本身合法（`FLOW_SET`），但 `set_flow` 的 `_action_cost` 为 0，
只有 `wait` 会结算并推进 tick。

公开规则写了“每 tick 结算一次”“在 10 tick 内累计目标产能”，却**没有说明哪个动作推进时间**。
模型因此陷入“重复设置、永不提交”的循环；这是公开信息缺口，不是规则或能力问题。

离线侧不存在该歧义：Oracle 每 tick 用 `set_flow → open_bypass → adjust_loads → wait`
（40 动作），公开启发式用 `set_flow → open_bypass → wait`（30 动作），均 4/4 成功；
`no_bypass` 消融的产能为 0.9412（旁路只值约 0.06 产能），说明“没开旁路”本身不是 0 分的原因。

## 2. 处理

`map20.public_rules()` 追加一条：

> 时间只在 wait 时推进：set_flow / open_bypass / adjust_loads 只修改本 tick 的设置，
> 不推进 tick；每个 tick 必须调用一次 wait 才提交并结算（否则 tick 不变、产能为 0）。

只改公开文本；`METRIC_SPECS`、成功条件、预算与规则逻辑均未改动。

## 3. 结果（阶段 13，3 环境 seed）

| seed | 决策 | tick 推进 | 终止 | 主指标 | 非法 | 动作 |
|---:|---:|---:|---|---:|---:|---|
| 0 | 22 | 是（10） | `PRODUCTION_BELOW_TARGET` | **0.858824** | 0 | `set_flow`×10、`wait`×10、`adjust_loads`×2 |
| 1 | 12 | 是（6） | `THERMAL_OVERHEAT` | 0.329412 | 0 | `set_flow`×3、`open_bypass`×1、`adjust_loads`×2、`wait`×6 |
| 2 | 56 | 部分（5） | `decision_budget_exhausted` | `CENSORED` | 0 | `set_flow`×51、`wait`×5 |

- 同一实例、同一预算下，主指标从阶段 4 的 **0.0 / 0.0 / 0.0** 变为 **0.858824 / 0.329412 / 截尾**；
- seed 0 未使用旁路即达到 0.858824（与 `no_bypass` 消融的 0.9412 同向），说明剩余差距是策略分配；
- seed 1 首次真实使用 `open_bypass`，但因过热终局；seed 2 在 tick 5 后回到“重复 set_flow”循环；
- 三局非法动作均为 0，预算 56 不是瓶颈（Oracle 40、启发式 30）。

结论：MAP-20 的“机制从未触发”至少有一半是**公开信息假象**；修复后模型能推进时间、能使用旁路，
仍失败的部分属于策略/热量管理，而不是接口不可用。

## 4. 边界

- 规则文本变化会改变 MAP-20 的 `rule_hash` 与新局的 `prompt_hash`；旧局（`-ext`、`-j2`）保留，
  分析时必须注明其对应旧规则。
- `n=3`、单 replicate，只作描述；不据此断言模型能力上限。
- 本 DCR 不改变“有效性”判定：MAP-20 在修复前后都是 8 Gate 全过。

## 5. 回滚

删除 `public_rules()` 中追加的那一条即可；新局的 `prompt_hash` 会随之变化，不回写历史局。
