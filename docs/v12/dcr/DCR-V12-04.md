# DCR-V12-04：长观测地图的瓶颈是**输入 token 上限**，不是请求数

- **状态**：`agent_reviewed`
- **严重度**：中（影响 MAP-30 的可测性判定）
- **发现于**：MAP-30 预算扩展（`lab-20261025T155152Z-93b31b11`）
- **类别**：测量配置 / 预算口径（不是环境或指标缺陷）

## 1. 事实

主矩阵里 MAP-30 九局 **8 局截尾**，当时的结论只能写"没测完"。做预算扩展（单局请求
上限 90 → 180）后，九局里仍有 **5 局**没有终局，`termination` 全部是：

```text
input_token_limit_exceeded
```

逐局：

| seed | 架构 | 终态 | 决策 | 请求 | 终止码 |
|---|---:|---|---:|---:|---|
| 0 | basic.v1 | FAILED | 81 | 81 | `ACCUSATION_REJECTED` |
| 0 | memory.v1 | FAILED | 102 | 102 | `ACCUSATION_REJECTED` |
| 0 | planning.v1 | BUDGET_REACHED | 111 | 112 | **`input_token_limit_exceeded`** |
| 1 | basic.v1 | BUDGET_REACHED | 147 | 147 | **`input_token_limit_exceeded`** |
| 1 | memory.v1 | BUDGET_REACHED | 113 | 113 | **`input_token_limit_exceeded`** |
| 1 | planning.v1 | BUDGET_REACHED | 110 | 111 | **`input_token_limit_exceeded`** |
| 2 | basic.v1 | FAILED | 109 | 109 | `ACCUSATION_REJECTED` |
| 2 | memory.v1 | FAILED | 52 | 52 | `ACCUSATION_REJECTED` |
| 2 | planning.v1 | BUDGET_REACHED | 107 | 108 | **`input_token_limit_exceeded`** |

也就是说：**请求数还有余量（147/180），但累计输入 token 先撞到 200 000 的上限。**

## 2. 根因

MAP-30 的公开 Observation 随进度线性增长：

- `casebook`（已记录条目）逐条累积；
- `recent_action_window` 保留 5 条；
- `entry_requirements` / `evidence_locations` / `npc_locations` 是固定大字典。

每回合都把整份 Observation 重新放进 prompt，因此 **输入 token 的累计量 ≈
回合数 × 单回合 Observation 大小**。MAP-30 单回合 Observation 明显大于其它图，
所以在 ~110–150 回合处会用完 200 000 累计输入额度。

V11/V12 的 `RunBudget` 是按**累计**输入 token 计量的（用于费用控制），这对成本是对的，
但它同时被当作"能跑多少回合"的预算，于是对长观测地图变成了隐性回合上限。

## 3. 后果

- 上一轮"MAP-30 是地板"的判断**部分错误**：4/9 局其实跑到了法庭并给出
  `ACCUSATION_REJECTED`，这是**真实机制失败**，不是"没测完"。
- 另 5 局被 token 上限截断，仍属"没测完"。
- 因此 MAP-30 的正确结论是：**"有 4 局在 81–109 回合走到法庭但指控被拒"**，
  而不是"0/9 能力为零"。

## 4. 处理

1. `create_budget_extension` 现在**同时**抬高输入 token 上限（默认
   `max(原值, 请求上限 × 2_500)`），并支持 `--ext-input-tokens` 显式覆盖。
   理由：只抬请求数而不抬 token，是假动作。
2. 新增独立实验 `v12-map30-token-600k`（180 请求 / 600 000 输入 token），
   验证"解除 token 瓶颈后是否全部走到法庭"。
3. 报告与账本仍按真实 token/费用结算，不做任何"折算回合"。

## 5. 建议（V13）

- `ExperimentBudget` 增加 `per_run_wall_clock` 与"按图校准的 token 预算"字段，
  并在预检里给出"预计可跑回合数 = token 上限 / 该图首回合 Observation 估算"；
- 或者更彻底：用**摘要式历史**（只保留最近 N 回合的完整 Observation + 更早的阶段摘要）
  降低累计输入，而不是无限抬高上限。
- 无论哪种，都必须新增预算版本并重跑，不能把不同 token 预算的局混算。
