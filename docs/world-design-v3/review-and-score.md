# V3 逐关设计评分与三视角审计

## 审计范围与方法

六项各计 0–2 分：玩法独特性、状态因果性、信息公平性、决策与后果、难度设计、验收完整性。总分只用于内容设计检查，不是科学量表，也不代表 LLM 能力或人类玩家体验。每个分数需能在对应状态规则、公开线索、可执行路线和反向用例中找到依据。

本次三种审查视角由不同测试输入模拟，不冒称三名真人或三个外部模型：

1. **规则一致性视角**：按关卡公开动作接口触发错误前置条件、动态边界、有限资源和终局边界；检查拒绝因果、公开读数及 reset。证据在 [`test_scenario_v3_rules.py`](../../tests/test_scenario_v3_rules.py)。
2. **可玩性与叙事视角**：每关从初始公开 Observation 执行一条参考路线，路线不读 Environment 私有状态；检查路线可达、线索/状态足以驱动动作、目标明确且回合不被隐藏终值打断。证据在 [`test_scenario_v3.py`](../../tests/test_scenario_v3.py) 与 [Oracle 回放报告](oracle-acceptance.md)。这是脚本试玩模拟，不是真人试玩。
3. **技术与兼容视角**：通过 Legacy 回归、Action schema 默认值、V3 显式 selector、Trace 脱敏和 CLI 限制检查隔离。证据是全量 pytest、Ruff、mypy、`git diff --check` 的最终记录；V3 使用独立的 `scenario_v3` Action/Trace contract。

测试模拟视角可复现，但不会发现所有自然语言叙事问题；本次没有外部人工或 LLM 评审。评分是按上面的证据作出的策划桌面复核，保留这一限制。

## 复核后修订

- PY-H 原稿的 `EYE 不在第一位` 在其他三条约束下冗余。已把线索局部改为 `SUN<SCARAB`、`SUN 与 SCARAB 相邻`、`SUN<REED`、`REED<EYE`；对 24 个排列枚举，唯一解保持不变，删掉任一线索后至少有两个候选。详见 [机制交叉核对](mechanics-crosscheck.md) 与谜题专项测试。
- AB-H 按原稿恢复三舱初值、独立递增周期和泵每次抽排 3；不再以单一机房递增规则近似整座站。
- PO-H 的天气作用按行动前公开相位结算；单人护送体热、室内恢复和主站燃料储备均由状态转移实施并有专门边界用例。
- SU-H 的 B 车维护锁在其驶入干线后触发，到站后显式解锁；A/C 顺序单独校验，公开 Oracle 采用 A-C-B。
- 金字塔宝库边、地铁列车路由、丛林藤门/河道与古堡密道现由真实状态控制，不能仅靠装饰性描述宣称机制存在。
