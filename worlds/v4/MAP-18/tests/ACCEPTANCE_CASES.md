# MAP-18 运行时实现后验收用例

这些用例是Phase 1设计草案，不是本阶段已执行的pytest结果。

1. Reset seed0：核对六列车、18人、三条线路、两条联络段、每站两泊位及公开计划到达tick `[6,6,7,2,2,7]`。
2. tick t动作在区间[t,t+1)执行；抵站记录tick t+1。R2-R3计划列车分别tick5、tick6通行，单段容量约束下无故障基准必须可行。
3. 告警模式在tick0–3与无告警模式观察完全一致、同seed。tick4只多一条泛化告警；消息不能包含线路、区段、ID、精确修复时长或Oracle路径。
4. 故障前检查私有`fault_id`不能影响观察、prompt或t0–t3动作；故障发生前不能公开R2-R3，tick5事件后才显示当前闭塞区段。
5. 故障必须在tick5操作前关闭并持续tick5–9；tick9放行返回`TRACK_CLOSED`且列车不动、全局tick进至10；tick10修复先于放行，合法放行成功。
6. 告警手写轨迹tick4让T_X由R2到B2；tick5同时T_X入B3、T_R1入R2，须原子校验R2/B3终态车数均为2；tick6 T_X离开B3。
7. 无告警完整服务轨迹在tick5看到实际闭塞后才让T_X离开R2；列车交班不导致R2临时占用3车，18/18送达、延误33、取消0、恢复7。
8. 告警完整服务轨迹18/18送达、延误30、取消0、恢复7；与无告警配对在相同事件和tick0–3动作下，仅警报可见性和tick4之后策略不同。
9. 折返策略tick5取消`TASK_R2_R3`并记3人损失；tick6和tick7锁住T_R2，tick8才可驶向R1。取消人数保留在18人服务分母。
10. 所有同tick动作先验证闭塞单车失败，再对其余合法移动做区段冲突和原子泊位检查；真正碰撞tick不发生部分移动或tick推进。无关合法列车可在闭塞线路上的另一列车收到`TRACK_CLOSED`时前进。
11. F01在tick4相向申请R2-R3返回`HEAD_ON_COLLISION`，尚未应用的tick5故障不改变失败理由。
12. F02对R2-R3于tick5–9的十次请求各返回`TRACK_CLOSED`；tick10复开后两车同tick反向争同段，返回`HEAD_ON_COLLISION`，该tick无位置变化。
13. F03取消两红线任务后其余任务最多送达12人；tick12按12/18低于70%返回`DEADLINE_SERVICE_BELOW_70`。
14. 重算告警计划：T_R2 `3×(11−6)=15`，T_R3 `3×(12−7)=15`，故延误30；无告警计划另加T_X `3×(8−7)=3`，总33。折返方案T_R3延误12、T_X延误3，总15。
15. Oracle每一步仅输出当前状态、当前闭塞、当前任务结果、公开班次和可见告警；不输出未来轨迹、隐藏事件字段或评分参考。固定动作seed0连续两次产生完全相同状态序列及Oracle字节。
