# Agent Arena 项目总纲

> 文档定位：这是完整的产品与研究蓝图。日常 workflow 默认读取 `研究总纲.md`，技术决策以 `docs/specs/` 为准，本文件保留为最终的详细参考。

## 1. 项目名称

**Agent Arena**

副标题：

**A Lightweight Benchmark for Evaluating Planning, Memory, Reflection, and Tool Use in LLM Agents**

中文可以理解为：

**一个用于研究 LLM Agent 在长程任务中规划、记忆、反思和工具调用能力的轻量级实验环境。**

---

# 2. 项目核心问题

这个项目不应该从“我要做一个能玩游戏的 AI”出发。

真正的问题应该是：

> **什么机制能让一个 LLM Agent 更可靠地完成长程、多步骤、部分可观测的任务？**

更具体一点：

> 当 Agent 面对一个未知环境，需要不断观察、做决策、调用工具、获得反馈，并最终完成目标时，Memory、Planning、Reflection 等机制究竟有没有帮助？

这是整个项目的灵魂。

游戏世界只是实验环境。

所以项目结构应该始终保持：

```text
Agent Arena
│
├── Environment
│   └── 提供任务和反馈
│
├── Agent
│   └── 自主决定下一步行动
│
├── Runner
│   └── 驱动 Agent-Environment 循环
│
└── Evaluation
    └── 衡量不同 Agent 的表现
```

---

# 3. 项目目标

第一阶段项目有四个目标。

第一，亲手实现一个完整的 Agent Loop，而不是简单调用某个 Agent 框架。

第二，建立一个**可重复、可控制的虚拟环境**，用于测试 Agent。

第三，实现至少两种不同的 Agent 策略。

第四，用实验数据比较不同 Agent 的表现。

最终 GitHub 用户打开你的仓库，应该很快理解：

> 这不是又一个 ChatGPT wrapper，而是一个用于研究 Agent behavior 的小型 benchmark。

---

# 4. 核心设计原则

整个项目有几个非常重要的原则。

## 4.1 Agent 不能看到完整世界

这是第一原则。

环境内部可以知道：

```python
world_state = {
    "reactor_room": {
        "drawer": {
            "contains": "access_card"
        }
    }
}
```

但是 Agent 不允许直接看到。

Agent 只能通过：

```text
look()
inspect()
move()
read_terminal()
```

逐步获得信息。

也就是说：

```text
真实世界状态
       ↓
Environment
       ↓
Observation
       ↓
Agent
```

Agent 永远只能拿到 observation。

这叫：

**Partial Observability**

也是让 Agent 真正需要“探索”和“记忆”的关键。

# 5. 第一版世界设定

第一个世界推荐固定为：

故事：

Agent 在一艘发生故障的飞船中醒来。

飞船主能源系统损坏。

逃生舱无法启动。

Agent 必须探索飞船，找到问题，并最终成功逃生。

这个环境足够直观，同时可以自然产生：

* exploration
* planning
* dependencies
* memory
* tool use
* failure
* recovery

# 7. 推荐的谜题设计

完整正确路径大致可以设计为：

```text
探索 Control Room
        ↓
发现主终端没有电
        ↓
探索其他房间
        ↓
在 Storage Room 找到 screwdriver
        ↓
Maintenance Room 发现 reactor diagnostic terminal
        ↓
得知 reactor panel 需要手动维修
        ↓
进入 Reactor Room
        ↓
使用 screwdriver 打开 panel
        ↓
发现保险丝损坏
        ↓
找到 replacement fuse
        ↓
安装 fuse
        ↓
恢复主电源
        ↓
返回 Control Room
        ↓
读取主终端
        ↓
获得 escape authorization code
        ↓
前往 Escape Pod
        ↓
输入 authorization code
        ↓
启动 escape pod
```

注意：

**Agent 不应该一开始知道这条路径。**

谜题实际上可以抽象成：

```text

     ↓

     ↓

     ↓
restore power
     ↓
access control terminal
     ↓

     ↓
```

这非常重要。

因为以后生成不同任务时，你实际上生成的是不同的 dependency graph。

# 17. 为什么工具不能太多

你第一个版本最容易犯的错误之一：

搞出 20 个工具。

没有必要。

Agent 的能力不来自工具数量，而来自：

```text
Observation
↓
Reasoning
↓
Tool selection
↓
Environment feedback
↓
New decision
```

6 个已经足够。

# 18. Action 数据结构

不要让模型输出随意文本作为动作。

使用结构化 Action：

```python
class Action(BaseModel):
    tool: str
    arguments: dict
```

例如：

```json
{
  "tool": "move",
  "arguments": {
    "destination": "storage_room"
  }
}
```

这样 Environment 才能可靠执行。

---

# 19. Observation 数据结构

推荐把 Observation 也做成结构化对象。

```python
class Observation(BaseModel):
    current_room: str
    description: str
    visible_objects: list[str]
    available_exits: list[str]
    inventory: list[str]
    last_action_result: str | None
```

但是给 LLM 时，可以转成自然语言。

比如：

```text
Current location:
Maintenance Room

Visible objects:
- diagnostic terminal
- tool cabinet

Available exits:
- corridor
- reactor room

Inventory:
- screwdriver

Previous action result:
You successfully picked up the screwdriver.
```

# 20. 核心 Agent Loop

这是整个项目最重要的一段代码。

建议你自己写。

逻辑：

```python
env.reset()

for step in range(max_steps):

    observation = env.observe()

    action = agent.decide(
        goal=env.goal,
        observation=observation
    )

    result, observation = env.step(action)

    agent.update(
        observation=observation,
        action=action,
        result=result
    )

    logger.record(...)

    if env.is_success():
        break

    if env.is_failure():
        break
```

看起来很简单。

但 Agent 的所有复杂行为都会围绕它产生。

---

# 21. Agent 接口

所有 Agent 都实现同一个接口。

```python
class BaseAgent:

    def decide(self, observation) -> Action:
        """根据公开 Observation 产生结构化 Action。"""
        ...

    def update(self, observation, action, result) -> None:
        """消费环境反馈；具体 Agent 可维护自己的局部状态。"""
        ...
```

以后：

```text
ReactAgent
MemoryAgent
PlannerAgent
ReflectAgent
```

全部继承它。

这样 benchmark 才能统一。

# 24. 关于 Thought

这里建议你做一个重要设计：

**不要依赖显示模型完整 Chain of Thought。**

你的系统真正需要的是：

```text
decision summary
action
```

例如让模型输出：

```json
{
  "reason": "The control terminal has no power, so I should explore another room for a way to restore it.",
  "tool": "move",
  "arguments": {
    "destination": "maintenance_room"
  }
}
```

这里的 `reason` 是简短决策解释。

不是让模型暴露几十行思维链。

UI 中显示：

```text
Decision
Explore the maintenance room to look for a way to restore power.

Action
move("maintenance_room")
```

已经足够理解 Agent 行为。

# 27. Memory Agent（Release 2）

第二个 Agent：

**MemoryAgent**

这是 Release 2 的研究对象，不属于第一版 Foundation/Release 1 闭环。

它不简单地把全部历史塞回模型。

而是维护一个结构化记忆。

例如：

```python
memory = {
    "facts": [],
    "visited_locations": [],
    "inventory_history": [],
    "failed_actions": [],
    "open_questions": []
}
```

实际运行可能形成：

```text
Facts
- Control terminal requires main power.
- Reactor room contains a damaged panel.
- Screwdriver opens the reactor panel.

Visited locations
- Control Room
- Corridor
- Storage Room
- Maintenance Room

Failed actions
- read_terminal(control_terminal): no power

Open questions
- How can main power be restored?
```

然后每轮决策时加入：

```text
Agent Memory
...
```

# 28. 为什么结构化 Memory 比完整 History 更值得做

一个新手很容易认为：

> Memory = 把聊天历史传进去。

这其实不够有意思。

真正值得研究的是：

> Agent 如何保留有用信息，同时丢弃无用信息？

也就是：

```text
Raw experience
     ↓
Memory extraction
     ↓
Structured memory
     ↓
Future decisions
```

这个问题以后会直接连接到：

* episodic memory
* semantic memory
* context compression
* retrieval
* long-horizon agents

# 29. Memory 更新机制

第一版不要再调用一个 LLM 来总结。

先自己写规则。

例如：

```python
memory.visited_rooms.add(
    observation.current_room
)
```

Inventory 直接同步。

失败动作：

```python
if result.success is False:
    memory.failed_actions.append(...)
```

Facts 可以从 Environment result 获取。

第二版以后再研究：

**LLM-based memory extraction**

这样你能比较：

```text
Rule Memory
vs
LLM Memory
```

# 30. Planning Agent

第三阶段加入：

**PlannerAgent**

它不是每一步都重新随机决定。

而是在任务开始或关键阶段生成高层计划。

例如：

```text
Current Plan

1. Explore accessible rooms for useful tools.
2. Identify the cause of the power failure.
3. Restore spaceship power.
4. Access the control system.
5. Determine how to activate the escape pod.
6. Escape.
```

注意：

计划应该是**高层抽象**。

不能让 Agent 凭空获得世界答案。

---

# 31. Planning 的运行方式

推荐：

```text
Goal
↓
Generate High-Level Plan
↓
Take Action
↓
Observe
↓
Update Progress
↓
Continue / Replan
```

Agent 内部状态：

```python
plan = [
    PlanStep(...),
    PlanStep(...),
]
```

每个 step：

```python
class PlanStep(BaseModel):
    description: str
    status: Literal[
        "pending",
        "active",
        "completed",
        "blocked"
    ]
```

---

# 32. Replanning

Planning 最大的问题之一：

**错误计划。**

因此必须支持 replanning。

例如连续 5 步无进展：

```text
Current plan does not appear to be making progress.

Review:
- current knowledge
- failed assumptions
- current objective

Create an updated plan.
```

这本身就是很好的实验变量。

---

# 33. Reflection Agent

下一阶段：

**ReflectAgent**

它主要解决：

```text
重复行动
陷入死循环
错误假设
长时间没有进展
```

Reflection 不应该每一步发生。

推荐触发条件：

```text
连续 4 次无有效状态变化

或者

同一个失败动作重复 2 次

或者

每 10 步一次
```

触发：

```text
Review your recent behavior.

What assumptions may be wrong?

What actions have not worked?

What important information may you be missing?

What should you do differently next?
```

然后得到一个短 Reflection：

```text
I have repeatedly tried to access the control terminal without power.
I should stop interacting with it and investigate the reactor system instead.
```

这个结果加入 Agent Context。

# 35. 什么是 Ablation Study

这是这个项目很值得学习的地方。

不要只比较：

```text
Agent A
Agent B
```

而是控制变量：

```text
Baseline

+ Memory

+ Planning

+ Reflection
```

观察每增加一个机制后发生什么。

例如最终结果可能：

| Variant      | Success | Avg Steps |
| ------------ | ------: | --------: |
| Baseline     |     46% |      27.3 |
| + Memory     |     68% |      23.1 |
| + Planning   |     74% |      20.7 |
| + Reflection |     82% |      19.9 |

这就是一个小型实验研究。

# 36. Evaluation Metrics

至少记录以下指标。

### Success Rate

```text
成功 Episode / 总 Episode
```

这是最重要指标。

---

### Average Steps

成功完成任务平均需要多少步。

```text
越低通常越有效率
```

---

### Tool Calls

每局调用多少次工具。

---

### Invalid Action Rate

例如：

```text
Agent 在 Control Room
却调用：

pickup("screwdriver")
```

而 screwdriver 根本不在这里。

这种行为应该计数。

---

### Repeated Action Rate

Agent 是否不断重复相同失败操作。

例如：

```text
read_terminal()
read_terminal()
read_terminal()
```

---

### Token Usage

用于研究成本。

```text
input tokens
output tokens
total tokens
```

---

### Completion Cost

以后可以计算：

```text
平均每次成功任务花多少钱
```

这个 metric 非常实际。

---

# 37. Progress Metric

这是一个很值得加入的指标。

世界内部存在 dependency milestones：

```text
find_tool
open_panel
repair_reactor
restore_power
get_code
unlock_escape_pod
escape
```

定义：

```text
progress = completed_milestones / total_milestones
```

这样即使 Agent 最终失败，也能判断：

```text
Agent A 到了 80%

Agent B 只到 20%
```

比单纯 Success/Failure 更有信息。

# 38. Difficulty

世界至少设计三个难度。

## Easy

依赖链短。

```text
screwdriver
↓
repair reactor
↓
get code
↓
escape
```

约 8–12 个合理行动。

---

## Medium

增加：

```text
额外房间
干扰物品
locked door
更多 terminal 信息
```

约 15–25 步。

---

## Hard

增加：

```text
无用物品
错误线索
多阶段依赖
需要回访旧房间
```

约 20–35 步。

第一周末实际只做 Easy + Medium 就足够。

# 39. Distractors

Agent Arena 很重要的一类设计是：

**干扰信息。**

例如 Storage Room 里：

```text
screwdriver
medical kit
flashlight
broken tablet
coffee mug
```

只有 screwdriver 有用。

这样可以测试：

> Agent 是否知道什么值得探索？

否则世界太干净：

```text
看到 screwdriver
→ 拿
→ 用
```

实际上几乎没有推理。

# 40. 环境不能完全靠自然语言实现

这是非常重要的技术设计。

错误方案：

```text
把所有世界状态写在 prompt 里

让 LLM 判断：
门开没开
物品有没有
动作成功没成功
```

这样 benchmark 会不可控。

正确方案：

```text
LLM 负责决策

Python Environment 负责现实
```

比如：

```python
if action.tool == "use":

    if (
        action.item == "screwdriver"
        and
        action.target == "reactor_panel"
        and
        "screwdriver" in inventory
    ):
        state.reactor_panel_open = True
```

**世界规则必须 deterministic。**

LLM 不允许修改现实。

# 41. Agent 与 Environment 的边界

必须始终保持：

```text
Agent:

我想做什么？
        ↓

Action
        ↓

Environment:

这个动作实际上会发生什么？
        ↓

Observation
```

Agent 决定意图。

Environment 决定事实。

这个思想以后做现实世界 Agent 同样适用。

# 60. Termination Conditions

Agent 不能无限跑。

至少三个终止条件：

成功：

```text
escaped == True
```

失败：

```text
step_count >= max_steps
```

系统错误：

```text
连续无效输出超过阈值
```

比如：

```text
3 次无法解析 Action
→ Episode Failed
```

# 61. Invalid LLM Output

现实一定会发生：

模型没有正确输出 tool call。

所以 Runner 要处理：

```text
JSON parse error
Unknown tool
Missing argument
Invalid destination
```

可以允许模型重试一次。

但一定记录：

```text
invalid_action_count += 1
```

这本身也是 Agent reliability 指标。

# 62. Progress Detection

Reflection 要知道：

“最近有没有进展？”

可以定义：

```python
world_signature = hash(
    relevant_world_state
)
```

如果：

```text
连续 N 步 world state 没有实质变化
```

就认为：

```text
no progress
```

注意 `move()` 可能变化位置，却并不一定是任务进展。

更好的做法是看 milestones。

# 63. Context Builder

这是整个 Agent 非常值得你自己写的一层：

```python
class ContextBuilder:
```

负责决定每轮到底给模型什么。

例如：

```text
System Prompt

Goal

Current Observation

Inventory

Memory

Current Plan

Recent History

Available Tools
```

Agent 很多性能差异其实来自：

> 你给了模型什么上下文？

以后你会发现 Context Engineering 和 Prompt Engineering 并不是一回事。

# 64. Recent History

不要无限添加历史。

例如只保留：

```text
last 5 steps
```

长期信息交给 Memory。

于是：

```text
Recent History
= 短期工作记忆

Structured Memory
= 长期记忆
```

这是一个很好的 Agent 架构。

# 65. Context Budget

可以记录：

```text
context tokens
```

然后研究：

> Memory Agent 虽然额外有 Memory，但是否反而减少了总 Context？

因为不需要把全部 History 放进去。

这是以后非常不错的实验问题。

# 66. 世界里的信息类型

建议你刻意设计三类信息。

第一类：

**Immediate observation**

```text
A terminal is in the room.
```

第二类：

**Persistent fact**

```text
The control terminal requires power.
```

第三类：

**Goal-relevant dependency**

```text
The escape pod requires authorization.
```

这样 Memory 才真的有意义。

---

# 67. 不要给 Agent Objective Progress

环境可以知道：

```text
Progress = 60%
```

但不要告诉 Agent。

否则它相当于获得上帝视角。

Progress 只用于 evaluation/UI debug。

# 68. Error Feedback

工具失败一定要提供有意义但不过度泄密的信息。

差：

```text

```

好：

```text

You cannot open it with your hands.
```

但是也不能直接说：

```text

```

否则没有探索。

# 74. 一个非常值得做的 Behavior Analysis

除了数字，还应该分析失败类型。

```text

Wrong planning assumptions
```

# 75. Failure Taxonomy

你可以最终定义：

```text
F1 — Repetition
重复无效动作

F2 — Forgetting
忘记已经发现的信息

F3 — Poor Exploration
没有探索关键区域

F4 — Premature Commitment
过早认定一种错误方案

F5 — Tool Misuse
错误调用工具

F6 — Planning Drift
行动逐渐偏离目标

F7 — Context Overload
历史过长导致决策质量下降
```

以后甚至可以自动/人工标注。

这时项目的上限会高很多。

# 92. 你开发时必须守住的三个边界

我尤其建议你把下面三句话放在自己的项目笔记最上面。

**第一：**

> LLM decides. Environment determines reality.

Agent 决策，Environment 决定事实。

**第二：**

> Agent only knows what it has observed.

没有观察过的信息，Agent 就不应该知道。

**第三：**

> Every architectural feature must be measurable.

如果你加入 Memory、Planning、Reflection，却无法比较它有没有帮助，那这个 feature 就还没设计完整。

---

# 93. 第一版真正的成功标准

不是：

```text
代码有 5000 行
```

不是：

```text
UI 很漂亮
```

也不是：

```text
用了 7 个 Agent 框架
```

而是你能运行：

```bash
python benchmark.py \
    --agent react \
    --world spaceship_easy \
    --runs 20
```

得到：

```text
ReactAgent

Success Rate:     45%
Average Steps:    24.8
Invalid Actions:  1.7
Repeated Actions: 4.2
Average Tokens:   7812
```

然后：

```bash
python benchmark.py \
    --agent memory \
    --world spaceship_easy \
    --runs 20
```

得到另一份结果。

最后你能够解释：

> **为什么两种 Agent 的行为不同。**

如果做到这一点，你的第一个 Agent 项目就已经非常成功了。

## 最终总架构

你现在可以把整个项目记成这一张图：

```text
                         AGENT ARENA

                            Goal
                              │
                              ▼
                   ┌───────────────────┐
                   │       Agent       │
                   │                   │
                   │  Context Builder  │
                   │  Memory           │
                   │  Planning         │
                   │  Reflection       │
                   └─────────┬─────────┘
                             │
                           Action
                             │
                             ▼
                   ┌───────────────────┐
                   │    Environment    │
                   │                   │
                   │  World State      │
                   │  Rules            │
                   │  Tools            │
                   │  Goal Conditions  │
                   └─────────┬─────────┘
                             │
                         Observation
                             │
                             └───────────────┐
                                             │
                                             ▼
                                          Agent


                 ┌────────────────────────────┐
                 │       Episode Runner       │
                 │                            │
                 │  Agent ↔ Environment Loop  │
                 │  Logging                   │

                 └─────────────┬──────────────┘
                               │
                               ▼

                 │                            │
```

**如果只保留一句总纲：**

> Agent Arena 不是“让 AI 玩一个游戏”，而是**构造一个可控世界，让不同 Agent architecture 在相同条件下完成长程任务，然后通过轨迹和数据研究它们为什么成功、为什么失败。**

这句话以后无论你写代码、加功能还是写 README，都可以拿来判断：**这个功能到底是在增强 Agent Arena，还是只是在把项目做复杂。**
