## 0. 执行指令与研究纪律（必须遵守）

你是本项目的执行 Agent（Muse）。**直接执行，不要把本文件仅仅改写成待办清单，也不要因为非关键歧义反复询问用户。** 遵循仓库 `AGENTS.md` 的分层读取、spec 驱动、测试、同步文档、提交等规则；执行前依次看 `AGENTS.md`、`研究总纲.md`、`docs/architecture.md`、`docs/scope/scope.md`、相关 spec、`docs/engineering-log.md` 的最近记录及 `git status`。先审计实际代码和历史记录，再决定修改范围。

1. **只认真实证据**：代码存在 ≠ 功能验证；Fake provider 成功 ≠ 真实 LLM 成功；不限步成功 ≠ 固定预算可靠；世界预定义阶段提示 ≠ 完全从观察中自行推断任务计划。报告明确区分 `verified`、`reported`、`not verifiable`、`not run`、`blocked`。
2. **绝不重复已有实验**：优先复用已有 `runs/`、`results/`、benchmark CSV/JSON、Git 文档与 trace。建立去重索引（world+version/hash、provider/model、Agent、prompt、全部开关、预算、采样设置、seed/replicate、实验代码版本）。只有缺乏有效对照或证据不完整时才增量运行。**不要为了好看的数字重跑失败实验，也不要默认做大量多 seed。**
3. **实验前冻结对照条件**：写清假设、唯一区别、预期观察、指标、运行配额、停止条件。保持模型/provider、world/hash、基础 prompt、环境规则、采样配置、预算和工具契约一致；不得把 Qwen/Muse 的结果混算，也不得将 `planner_assisted`/`guarded` 计入“纯自主”。
4. **自主性标注要诚实**：`--autonomous` 只表明某些辅助/Runner 行为关闭，不能自动证明“无先验”。`--phase-context` 读取世界声明 `PublicMilestone`，可能将未探索到的关键物品和阶段先验暴露给模型；单独列为 **world-declared guidance / 世界预定义任务辅助**。同时区分纯 observation、observation-derived 历史/记忆/循环反馈，以及给定路线或动作建议。
5. **保留原有行为**：不要破坏 3 世界 9 图、现有 `Action` schema、`Observation`/`WorldState` 隔离、trace 兼容性、历史基线；新功能尽可能增加独立选项/新 world version，默认旧模式不变。
6. **密钥与隐私**：不提交 `.env`、API Key、网关会话头、原始模型响应、完整思维链；遵守 `runs/`、`results/` 默认不入 Git 的规则。共享数据仅发布经过检查的脱敏、可核验摘要/manifest/必要的匿名化片段，不绕开 `.gitignore` 强推日志。
7. **分阶段交付**：每个任务最少包含“实施 → 测试 → 可复现报告 → 更新 scope/工程记录 → 独立 commit”；有权限且仓库工作流允许时 push。**不得因后一个大任务未完成而把前面已验证成果一直留在未提交状态。**
8. **失败处理**：CI 红灯时先修复再开启新的昂贵模型实验。发生 provider_error、超时、限流或进程中断时记入原始尝试账本；不能悄悄剔除失败尝试后仍将结果叫作无条件 45/45。允许明确声明某部分暂不可做，提供最小诊断与恢复条件，不虚构结果。
9. **成本控制**：先离线、后在线；先小规模诊断、后受控扩展。所有真实模型实验记录请求数、输入/输出 token、延迟、成功率和实际预算。并发量以服务商限流和机器稳定性为前提，不因本机 GPU/网关空闲就启动冗余大矩阵。

## T2｜P0：离线重评 45 局——成功率、路径效率与失败诊断

### 研究问题
当前不限步数成功，换成固定动作预算时还有多大优势？真正浪费动作的是探索、走回头路、重复读取终端，还是终点工具误用？

### 执行步骤

1. 尽量只读取 T1 已确认的完整 trace，不调用模型。基于 Action/ToolResult 重算通关与动作数，并与 benchmark JSON/CSV 交叉校验。
2. 计算 `Success@K`：**K ∈ {30, 60, 100, 150, 200}**。对成功且步数 ≤ K 的已知 trace 可做离线预算重裁剪；对提前 `provider_error`/截断、无足够后续证据的 trace 应标记 censored/unknown，不能简单视为有明确 K 步失败的同等样本。明确这是**离线回放估计**，不等价于真正“告知模型预算后运行”的在线 `Success@K`。
3. 同时输出总体与每个世界/难度：成功率、步数均值/中位数/极值/离散度、失败终止分类、平均 token、调用次数、延迟、无进展动作数、重复 Action 比例、连续 `look`、同一无变化状态下的重复 terminal 交互。
4. 以 spec/环境规则测试中确认的最短公开通关动作数作参考下界，计算 `path_efficiency = shortest_reference_actions / executed_actions` 或等价开销倍数，**在图中解释此最短路径是已知地图/谜题下界，不是 Agent 当时已知的路径**。
5. 按阶段（寻找工具、修复设施、恢复电源、读取授权、最终逃生）统计每阶段耗费的 Action 与具体失败类别；阶段边界仅用于**评估**，不反向写进无辅助 Agent 的观察输入。
6. 特别复核：飞船的“困难中位数步数低于中等”；9 图均值单调递增不等于严格、显著的难度排序；样本量每档仅 5 次，报告不确定性和分布而非过度显著性叙事。
7. 增加命令行可重算的分析工具/测试（尽量扩展现有 `analyze-traces`）；处理旧 schema 缺失字段，输出 N/A 而不是零。

### 验收条件
- 生成 9 配置完整统计表、跨配置对照图/可机读 CSV、每个关键失败现象的 episode/step 引用。
- 指标由确认的 trace 可重算；测试覆盖 `Success@K` 边界、缺字段、重复文件、异常重跑、截断。
- 给出 **TOP 3 可操作的效率瓶颈**，分别说明证据强弱；不能只用主观推测。
- 交付 `02-offline-metrics.md`。

## T3｜P1：Memory / History / Recovery / Phase 的受控消融

### 核心目的
拆开“Memory + history5 + recovery + phase + 不限步”的成功组合，回答哪个变量有效、哪些变量互补，以及能否把贡献归因于真实策略改善，而非单纯给了更大步数预算或任务先验。

### 先做的审计
- 整理仓库现有基线：Muse 原始 React/Memory/Planning 0/5、Muse 60 步 `history`/`phase`/`recovery` 已完成的单变量及组合对照、早期 Qwen 对照；**同条件可复用，不同模型或预算不能硬凑成一张公平表**。
- 根据 `src/agent_arena/evaluation/runner.py` 的实际实现标注：
  - `M`：规则驱动结构化 Memory（对比 `react` 与 `memory`）。
  - `H`：最近 5 步公开观察-动作-结果历史。
  - `R`：stuck recovery / 公开循环检测反馈。
  - `P`：`PublicMilestone` 世界声明阶段提示（**任务先验辅助**），不等同于仅从 Observation 派生的纯上下文。
  - `B`：步数预算（当前主成绩 B=unlimited，历史对照可能 B=30/60）。

### 实验设计

**第一层：相同 Memory Agent 下的 H/R/P 三因素 2×2×2 对照。** 对于历史缺失的组合，在同一 Muse provider、同一 prompt/配置、相同地图版本、相同步数预算下做小规模补测，重点是交互效应，而不是再大量复验已有 `H=R=P=1` 成功组合。

| 条件 | H | R | P | 解释 |
|---|---:|---:|---:|---|
| C000 | 0 | 0 | 0 | 基础 Memory |
| C100 | 1 | 0 | 0 | 仅近期历史 |
| C010 | 0 | 1 | 0 | 仅卡死恢复 |
| C001 | 0 | 0 | 1 | 仅世界阶段提示 |
| C110 | 1 | 1 | 0 | 历史 + 恢复 |
| C101 | 1 | 0 | 1 | 历史 + 阶段 |
| C011 | 0 | 1 | 1 | 恢复 + 阶段 |
| C111 | 1 | 1 | 1 | 已取得高成功率的组合 |

- **实验规模**：优先选择 1 张中等难度地图 + 1 张困难地图，各配置最多 5 次可比较的独立模型调用尝试（历史同条件先抵扣）；能从已有数据得出结论就不新跑。先做 seed/replicate 0 的 pilot 验证契约，再补齐有信息增益的缺口；不要立即把 8×9 图全部跑满。
- **预算控制**：至少用一个固定执行预算（推荐 100 或 150 actions，实际根据 T2 分布写入预注册表）。可并列给出 unlimited 离线裁剪曲线，但不得把 30 步基线与 unlimited 组合的成功率直接相减当作架构收益。
- **第二层：Memory 对比 React**。如果预算允许，在 H/R/P 固定不变的条件下比较 Memory 与 React，隔离 Memory 本身的增益；如果当前代码不支持在 React 下等价运行这些上下文，先实现最小共用适配，再对照。
- **第三层：Phase 先验审计**。拆分 `no phase`、`observation-derived progress`（只能从已见事实归纳，不能预报未知目标）和 `world-declared milestone`；测试 phase 是否在未发现物品前已经暴露 item id。新增单测防止错误标注为“无引导纯自主”。
- 所有组合必须记录模型标识、prompt/脚本 hash、具体输入字段差异、预算和网关尝试状态。

### 主要指标与分析要求
成功率（附样本量）、`Success@K`、到目标的步数、重复/无进展比例、各阶段进展、token/延迟成本；小样本以效应大小、逐局轨迹和成对比较为主，置信区间仅作描述性估计，**不把 5 次试验包装为统计显著证据**。

### 验收条件
- 完成可核查的因素矩阵（已存在/新运行/缺失分别标注）；至少可以解释 H/R/P 的主效应或交互为什么目前可判/不可判。
- 给出明确的自主性等级，并修订 README/研究摘要中任何混淆“世界预设里程碑”和“纯观察规划”的描述。
- 交付 `03-factor-ablation.md`，含不重复实验清单、预算表和每个结论对应 trace。

## T4｜P1：优化终点误操作与读码后迷路，验证效率收益

### 待验证的具体问题
已有记录指出：灯塔终点曾对小艇多次错误调用 `read_terminal`；飞船有多次重复读码、在终点前回游的长轨迹。目标不是单纯把提示词写得更像攻略，而是**让 Agent 将已知授权信息转化为正确动作，减少迷路与空转**。

### 执行顺序

1. 从 T2 提取这两类现象的具体 trace/step，形成可复用的错误分类：`WRONG_TOOL_AT_TERMINAL`、`REPEATED_CODE_READ`、`POST_CODE_NAVIGATION_LOOP` 等（不强迫现有 Failure taxonomy 结构大改）。
2. 首先进行**无模型运行的诊断与契约测试**：检查 `visible_objects`、`inspect` 对象描述、合法 `read_terminal`/`use` 目标、`CODE_READ` 后公开反馈；检验是否存在描述歧义或工具契约不一致。
3. 选择极小的候选修正，严格分开：
   - **E1：通用 tool 语义解释/Action 示例修正**（只解释 `read_terminal` 与 `use` 的职责，不硬编码逃生目标、地图路径或授权码）。
   - **E2：终点物体 `inspect`/ToolResult 的公开描述更清晰**（例如说明它是可交互载具而非终端；如果是环境文本变化，应创建可识别的新世界/文本版本，避免污染旧基线）。
   - **E3：已读码后的通用事实恢复提醒**（仅从公开成功的 `CODE_READ`、已访问出口、最近动作推导，不能回看隐藏地图、直接告知最优路线）。
4. **一次只修改一种机制**，先使用固定失败 trace 做离线可达性/机制验证，再在同模型同配置同预算的少量局上比较 `C111` 对照与 E1/E2/E3。若 E1 已有效，不自动把三项叠加后宣称每项有效；如需组合，增加专门组合条件。
5. 保持 `Action schema`、环境可解性、难度地图、旧行为兼容；必要时设计单独新文本版本。检验优化后并未因暗示唯一答案而把自主任务变成 `planner_assisted`。

### 验收条件
- 以量化指标比较修正前后：读码后无进展动作、终点误用、到终点延迟、`Success@K`、平均总步数、token；出现退化必须报告。
- 给出每种干预的成功/失败 trace，说明是否存在“靠近答案式提示”造成的公平性问题。
- 更新所涉契约测试；交付 `04-efficiency-ablation.md`，选择有证据的改动保留，未证明的改动撤回或隔离。

## T5｜P1：PlanningAgent 在同等公开上下文下的公平对照

### 研究问题
早期 PlanningAgent v1 在 Qwen/Muse 上 0/5，并伴随高频 Planner 调用、子目标到有效动作 (`Subgoal → Action grounding`) 失败。若让它获得与成功 Memory 组合**同样的可用公开上下文**，显式规划究竟能否改善长程任务，而不是继续增加无效重规划？

### 执行步骤

1. 阅读 `docs/experiments/planning-v1-failure-analysis.md`、spec 0006、`agents/planning.py`、`planning/monitor.py`、`evaluation/runner.py`，明确旧失败的证据与此前未验证的 `grounding` 细节。
2. 核实 PlanningAgent 是否正确接收到与 Memory 对照**等价的 H/R/P 信息**，以及 Executor prompt、模型能力、工具契约是否一致。必要时实现最小适配，**冻结旧 Planning v1 作为基线**，新增带版本名的新对照条件，不能覆盖原始结果。
3. 优先在 T3 的中等 + 困难代表地图上做小规模同预算对照：
   - `M-C111`：Memory + H/R/P（主基线）。
   - `P-v1-context`：Planning v1 + 同等 H/R/P 公开信息；记录 Planner 与 Executor 的额外调用成本。
   - 只有当 `P-v1-context` 的失败证据指向特定问题时，再追加**一个**最小单变量 grounding 修正（例如避免高层子目标反复落成不推进的 `look`）；不得直接新建大而全的 Planning v2。
4. 将不同架构必然导致的 prompt/调用次数差异列为研究变量并明确说明；世界、模型、budget、可访问公开信息应相同。特别防止 Planner 偷读 WorldState、唯一建议动作或评估器里程碑。
5. 记录 replan 后首个 Action、子目标完成率、Planner call ratio、重复 `look`/失败动作、成功率/步数、input/output tokens、成本、延迟。对每个失败 trace 抽样标注 `WRONG_ACTION`、`FORGOTTEN_FACT`、`INEFFECTIVE_REPLAN` 等，用证据区分 Planner 和 Executor 问题。

### 验收条件
- 提供同预算、同地图、同模型、同公开信息的对照表，并按 Planner/Executor 分拆调用和成本。
- 如果 Planning 仍失败，要能回答“卡在什么阶段、究竟是任务计划错误还是动作落地失败”；**0/5 也是合法研究结果**，不能为求漂亮数据临时给它唯一下一动作答案。
- 只在有明确收益或诊断依据时提议 Planning v2；交付 `05-planning-controlled.md`。

## T6｜P2：真正随机 seed、未见实例与不同任务结构的泛化验证

### 研究目的
把“同一固定地图重复采样成功”与“面对不同环境实例也能成功”区分开；进一步区分“换背景/名字”与“真实任务推理结构变化”。

### 执行步骤

1. 再次审计 seed 在三个世界的使用：若只储存在 `WorldState.seed`、不影响地图与状态，明确记录 `seed` 当前是 **replicate id** 而非 world generation seed，不得继续写“5 随机地图”。
2. 不更改原有九张地图和旧 world version。在**新版本或新生成器**中实现确定性 seed 实例化，至少让一个有意义的维度随 seed 变化：工具/物品位置、可用岔路、关键依赖顺序或诱饵分布；同时要求固定 seed 可复现、不同 seed 可产生不同实例、每个实例有合法公开解。为每个实例记录 `world_definition_hash` 与 oracle 可解性检验。
3. 独立创建**真正不同的任务结构**的小测试族（优先少而精）：例如资源优先级与分支选择，或多条件并行收集再决策；不能仅通过把飞船的 `fuse/power/code` 改名来宣称跨任务泛化。先用已有六个工具表达，确实无法表达时再设计新 Action/world version 和兼容测试。
4. 新任务的 `PublicMilestone` 必须区分环境评价标准、Agent 可见提示和从观察推导的阶段；oracle/隐藏状态仅留在 Environment/test evaluator，不给纯自主 Agent。
5. 采用小规模训练外/开发外评测：固定开发地图调试，预先锁定未见 seed/地图用于 holdout；优先 3–5 个不同实例 × 2 个代表性任务结构，条件使用 T3/T4 冻结的最优**合法**机制，同时至少保留基础对照。若本轮资源不足，完成生成器、测试和少量 smoke，明确后续真实模型验证未完成。
6. 建议评估维度：固定环境重跑可靠性、seed 实例迁移、任务结构迁移三层分别汇报，绝不合并成一个夸大的“泛化成功率”。

### 验收条件
- `seed` 改变环境的测试成立；相同 seed 可精确重现；生成样本可解且不泄漏隐藏状态；旧世界的所有行为与历史 benchmark 保持一致。
- 至少产出一组真实随机实例与一个新任务结构的独立评测或明确的可运行前置设施；保留所有失败样本。
- 交付 `06-generalization.md`，说明迁移边界、难度设计的局限及未覆盖的能力。

## T7｜P3：条件触发 ReflectionAgent 与最小 Streamlit 实验界面

> 两者都属于第 7 项任务，但应作为**两个独立验收子阶段**，不能为了做界面提前停止研究，或为了实现 Reflection 把其收益直接当作既定事实。

### T7-A｜ReflectionAgent（研究性、条件触发）

1. 只有在 T2–T5 表明仍有可被反思修复的重复错误，并且研究预算允许时，设计最小新 `ReflectionAgent` 版本；如果没有价值证据，先交付设计论证和 `deferred` 决策，不人为制造新框架。
2. 反思触发只依赖公开历史：例如连续无进展、重复失败动作、当前子目标无法落成 Action；选择明确阈值，并记录触发原因、输入摘要、反思成本及其后的实际动作变化。
3. 严格禁止读取 `WorldState`、oracle、完整思维链；Reflection 不得直接替模型执行工具，不得隐藏第二模型调用产生的 token 成本。
4. 同模型、同 H/R/P、同 world、同 budget 比较 `Reflection off/on`；主要判断是否改善 `Success@K`、重复/拒绝动作和 token-efficiency，不能只看无限步成功率。

**验收**：若实施，则新 Agent 生命周期、trace provenance、回归测试齐全，并有可比较真实实验；未达门槛则明确未实施理由，不能写“Reflection 已证明有效”。

### T7-B｜Streamlit UI（只做研究可视化 MVP）

1. 在 T1/T2 可靠数据契约稳定后，实现轻量界面：选择已有 provider/模型/Agent/world/seed/预算，运行单局或已支持的 benchmark，展示每步 Observation、Action、ToolResult、阶段、失败原因、token/延迟、最终结果、条件/辅助来源。
2. 最重要的视图：不同 Agent/条件下的 `Success@K`、步数分布、成本和失败类型比较；`planner_assisted`、`world-declared phase guidance`、真正纯 observation 条件必须明确标记。
3. 不添加账户、数据库、云部署、多 Agent 编排或大前端。无真实模型 Key 时 UI 仍可用 Fake trace/已有脱敏样本离线浏览；不要要求 UI 才能运行 CLI benchmark。
4. 对路径输入、trace 读取、异常局、无模型/无结果、长 trace、状态清理添加基本检查；UI 不得读取/显示 `.env` 与密钥。

**验收**：可加载一份已有 trace、复盘完整 Action 链、对比至少两种实验条件；若资源受限，保留最小只读界面而非做复杂控制台。交付 `07-reflection-and-ui.md`。
