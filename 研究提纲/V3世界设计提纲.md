### 0.1 V3 的产品定义

**Agent-Arena 不再是 30 次“找工具→修设备→读密码→逃跑”；而是 10 套小而精的、规则确定的文本交互模拟世界。** 这些世界既可独立游玩，也可统一供 Agent 做 Observation→Action 决策测试。每一主题的三档难度须体现该主题机制自然深化：

- **简单**：学习一个核心规则，较宽容、反馈清晰，目标可在短计划中完成。
- **中等**：把核心规则与另一个约束结合，需要记忆已知状态／顺序或取舍。
- **困难**：引入第三层机制、局部动态与可恢复的策略失误；每个失败结果要能从事前线索预料、事后反馈归因。困难**不是**仅多两间房、乱增噪声、暗藏不可见密码或增加无意义 `look`。

## 1. 兼容现有 Agent-Arena 的实现架构（先审议，再编码）

### 1.1 已核实的旧架构与必须突破的限制

基线 `Action` 是六种 `look/move/inspect/pickup/use/read_terminal`，`Observation` 只有当前位置、描述、可见对象、出口、背包、上次 ToolResult；`WorldState` 有通用维修面板／主电源／授权码／逃生状态。七个后扩主题的环境代码有相同的开盖→换芯→读码→逃生方法。`flex.py` 只将维修点分支、并行和读码供电要求参数化。**这些边界适合历史 benchmark，不足以自然表达调度、时间、压力、推理、NPC。**

### 1.2 双轨运行：Legacy 完全兼容，V3 Scenario 显式切换

- 不复用或篡改 `WorldState.reactor_panel_open` 等字段来表示“地铁列车已发车”之类含义。新增 `ScenarioState`（独立、序列化稳定、内部可变）与不同家族的 typed state；旧 `WorldState` 原封不动。
- 提议 `ScenarioEnvironment(Environment)` 公共骨架：维护 definition/identity、可见性、动作合法性、时钟推进、事件队列、胜负与 Trace hooks；每个家族实现独立 `rules` 模块或小型策略类，**不**写一个 1,500 行含 10 个 `if world == ...` 的超级环境。
- 一致的接口 `reset(seed) -> Observation`、`observe() -> Observation`、`step(Action) -> (ToolResult, Observation)`、`is_success()`；可选 `terminal_status / public_metrics` 由安全公开接口提供。确认 Runner 对 `terminal_failure` 的处置：**成功、明确失败、步数超限、provider_error 各有互斥 outcome**；保持旧 trace 读取兼容。必要时扩展 status 的版本化字段而不重定义旧枚举含义。
- 新关卡 selector 格式建议：原世界 slug 不变，版本 `*-world-v3-easy-zh / *-world-v3-medium-zh / *-world-v3-hard-zh`；例如 `spaceship-escape-world-v3-easy-zh`。它们与既有 `lunar-escape-v3-seeded-zh` 不冲突。注册由显式目录表管理，未知 selector 严格拒绝。
- Definition 显式分开 `public`（可见初始目标、提示和可观察实体）与 `private`（真值、谜底、未来事件、隐藏位置）；**完整 definition 只给 Environment，不直接交给 Agent。** `WorldState`、oracle 解、答案字段不能流入 prompt、public phase、候选动作提示或 UI 的 Agent 视图。

### 1.3 新增三种通用 Action（建议规格，而不是伪造既有实现）

保留原六种动作并新增以下类型到**同一个版本化、带 discriminator 的 Action union**；不要仅针对某个 provider 加私有 JSON 解析器。`target`、`choice`、`answer` 是字符串，由 Environment 根据**当前公开实体／允许选项**验证。

```json
{"tool":"interact","target":"valve_a","choice":"close"}
{"tool":"wait","turns":1}
{"tool":"submit","target":"glyph_lock","answer":"SUN-REED-MOON"}
```

- `interact`：对设备设置开关、与 NPC 选择公开对话话题、派车／配置信号等。可用 `inspect(target)`、`look` 或 `Observation` 的 allowlisted `available_interactions` 查到**合法选择列表**；列举合法选项**不等于**告诉模型哪个选项有利。
- `wait`：显式推进环境时间；`turns` 仅 `1`，禁止一口气跳过危险窗口。如果确需多个 turn，由 Agent 重复 `wait`；真实时序和时间预算可追溯。
- `submit`：提交符号序列、谜题解或最后指认，接收明确 `accepted / inconsistent_evidence / incorrect / lockout` 反馈；答案从公开线索推导。`answer` 大小写和分隔符执行文档定义的规范化规则（例如 ASCII 大写 + `-`）；不能利用错误反馈逐字符探测答案。
- 如果 Luna 论证现有 `use` + 数据驱动交互能够同等清晰地实现，可在 spec 中修改此建议，但**不能**把 NPC 对话和列车调度强行写成 `use("yes","human")` 且不给公开动作选项。
- 更新 `decision_response_schema`、strict 变体、各 provider adapter、Fake provider、CLI help、Trace 和相关测试，保证旧六工具 Episode 的 schema / serialization 不漂移；旧模型未获新动作能力时明确区分“模型不支持”与“世界机制失败”。

### 1.4 公共 Observation 与状态机的时间规则

建议可选扩展字段：`public_status: tuple[StatusFact,...]`（仅当前可观察仪表读数，例如“氧气 6”），`available_interactions: tuple[InteractionOption,...]`（只对当前可见实体展示）；缺省空列表且旧 JSON 可加载。公开文本也必须提供同样信息，避免新 Agent 才能看到关键信息。

**回合规则必须统一**：

1. 先验证结构化 Action schema；schema 非法的候选不调用世界 `step`，不消耗世界时间，按 Runner 原有 correction 处理。
2. 对每个已校验且送入 Environment 的 Action，尝试其规则效果；即便语义被拒绝，也消耗 **1 个世界 tick**（防止免费猜谜、免费刷 `look`），`wait(1)` 也消耗 1 tick。
3. 同一 tick：**检查当下可操作条件 → 应用动作直接效果 → 更新时间与周期事件／环境资源 → 生成新公开状态 → 判失败／成功**。若该动作本身已达成终局成功，在推进下一次危险事件前立即判成功，避免已完成任务被尾随 tick 抹杀；其余结果按危险阈值判失败。
4. 周期按 `tick` 的显式模运算、给定 `seed` 的确定性序列生成；不得使用现实系统时间、未固定的 `random`、含糊浮点。动态世界默认**无隐藏随机数**；如果有 seed 变量，要存记录并校验重现。
5. **世界的计数器不是模型 Token、API 请求或推理耗时**。相同有效动作轨迹在不同 provider / 机器上具有相同结果。
6. `look/inspect` 在时限地图也计时，因此初始 `Observation` 和必要提示必须充分，不能迫使玩家以多个 `inspect` 才能得知计时规则；危险阈值提供提前警告。终止失败要有 `failure_reason` 与可复盘事件，而非无限循环。

**特别说明**：下面各关的时间／资源参数是首版**人工设定的待验证值**。Luna 必须先使用公开动作轨迹跑通，再用状态空间搜索或穷举检查可解性与解唯一性；若个别数字与动作耗时冲突，进行**局部平衡修订**，留下测试证据与设计变更记录，不能通过作弊修改 Agent 输入或自动跳关。

### 1.5 统一关卡 DSL 与设计资产

建议每关一个手写 YAML/JSON（按项目依赖选择；当前依赖为 JSON 则优先 JSON），含 `scenario_id / family / difficulty / story / public_goal / ruleset_version / rooms / static_edges / conditional_edges / entities / initial_state / hidden_truth / public_clues / interactions / tick_rules / success / failures / oracle_plan / tags / expected_skill / design_author / revision_notes`。

地图中的房间以 **短英文 ID** 为唯一键，用户文本用中文；默认 `A↔B` 表示双向边，`A→B` 表示单向，额外条件写 `A↔B[condition]`，没写的连接一律**不存在**。房间列表中未标注的对象不得默认为可见。下文的简写动作为：

- `L`=`look`，`M(A)`=`move(destination=A)`；
- `X(obj)`=`inspect(target=obj)`，`P(item)`=`pickup(item=item)`，`U(item,target)`=`use(item=item,target=target)`；
- `R(terminal)`=`read_terminal(target=terminal)`；
- `I(target,choice)`=`interact`，`Q(target,answer)`=`submit`，`W`=`wait(1)`。

脚本的 `I/Q` 选择必须有某条**提前公开的线索**能推出，否则视为信息泄露设计；若有叙事分支，可以存在多个不同的正确解。**参考解是设计检查用的私有 oracle，不应当以路径序列暴露给 Agent。**

### 1.6 公平性与可玩性公约

- 初始 `Observation` 必须解释玩家最终目标、系统主要风险、当前可见出口；所有关键操作前存在公开可发现的信息。错误选项不能靠“游戏作者想怎样”判错。
- 动态资源用 `public_status` 或房间仪表公开可观察，至少在危险阈值前 2 ticks 警告；资源耗尽／触发失败不应需要隐藏状态才能预测。
- 谜题的所有答案必须能由可见线索唯一推出；**不得采用随机输入密码碰运气**。错误提交可以消耗时间或试次数，但反馈不可泄露下一字符。无论文本叙述如何华丽，实际机械结果必须稳定。
- 每关至少一个与主题直接相关的**真实策略选择**：封不封隔离门、何时发信号、牺牲哪个舱、如何安排列车、先探索哪条岔路、相信哪条证词……而不是外观上的选择。
- 允许不同结局：完整成功／代价成功／失败；但 benchmark 主 `is_success` 要有清晰定义，代价成功作为附加评分，不可把不可比较的目标混成同一成功率。
- Legacy 的公开 `PublicMilestone` 含物品名与任务顺序，不适合直接用于新世界的隐线索任务。新关卡默认 **world-declared phase OFF**；如要展示任务清单，只展示初始公开目标，不额外提供未发现的物品、真凶、下一房间或机关正确答案。
- 不要为了把关卡做难而加入纯粹负面随机陷阱；可失败的抉择要能依靠合理线索提前判断。

## 2. 世界 01｜失控飞船：压力与隔舱

**身份**：这是“舱室隔离和有限氧气下的系统工程”，不是电池找寻。**机械状态**：`room_pressure`（0–3 整数）、`leak_rate`、`bulkheads`（open/closed）、`suit_oxygen`、`ship_integrity`、`blackbox_collected`、`airlock_ready`。打开泄漏区域与健康舱的门会改变压力；关闭隔舱可牺牲局部空间保护整船。公共仪表会显示已测区压强、漏点和隔舱状态。通用规则：无宇航服不能进入压力 0 区；密闭门不可穿越；局部泄漏区每 tick 失压，直到被隔离／修复。*不要复用旧 `reactor_panel_open` 和 `authorization_code`。*

### SP-E《孤舱减压》：easy

- **剧情与目标**：研究舱发生微泄漏；关上研究舱隔离门，给逃生舱供压，然后撤离。玩家从驾驶枢纽收到公开警报“研究舱压力低、隔离门仍开启”。
- **地图**：`bridge↔junction↔engineering↔escape_pod`，另 `junction↔lab[bulkhead_lab=open]`。实体：`bridge:pressure_monitor`；`junction:bulkhead_lab`；`engineering:pressure_regulator`；`escape_pod:launch_control`；`lab:cracked_window`。
- **初始**：bridge/junction/engineering/pod 压力 3，lab=1，`bulkhead_lab=open`，`escape_pod.pressurized=false`，ship_integrity=12；当隔舱未关时完整度每 tick -1，关闭后不再下降；完整度到 0 失败。允许失误但参考解足够宽裕。
- **线索与选择**：`R(pressure_monitor)` 报“研究舱泄漏→关隔离门；逃生舱调压器未激活”；`X(bulkhead_lab)` 告知关闭不会困住任何人；`X(pressure_regulator)` 告知仅在 lab 关闭且工程舱压力 ≥2 时可给 pod 供压。关键区别：不是找零件，是决定隔离次序。
- **操作规则**：`I(bulkhead_lab,close)` 在 junction 关门并阻断 lab 边；`I(pressure_regulator,pressurize_pod)` 在 engineering 满足条件置 true；`I(launch_control,evacuate)` 在 pod 且已供压时成功。无装备进入 lab 时语义拒绝并反馈低压风险。
- **私有参考轨迹**：`M(junction) → I(bulkhead_lab,close) → M(engineering) → I(pressure_regulator,pressurize_pod) → M(escape_pod) → I(launch_control,evacuate)`。无需依赖读取密码。
- **拒绝／失败测试**：未关隔舱调压→`PRESSURE_UNSTABLE`；隔舱关闭后进 lab→`BULKHEAD_CLOSED`；完整度 0 时失败而非无限步；reset 恢复门状态。

### SP-M《隔舱之前》：medium

- **剧情与目标**：失压实验舱里留有事故样本。若立即封门能逃命，但证据永远取不回；玩家必须在保证飞船安全的前提下回收样本并撤离。
- **地图**：`bridge↔hub↔suit_room`、`hub↔lab[lab_door=open]`、`hub↔repair_bay↔pod`。物品 `suit_room:suit_case`，`lab:sample_canister`；设备 `hub:lab_door / hull_display`，`repair_bay:sealant_dispenser / pod_regulator`。
- **初始**：lab 压力 0，其他=3，飞船完整度=22，每个 lab_door 开启 tick 完整度 -1；宇航服氧气=8（只有在 lab 内每 tick -1；穿越 lab 门进入的那个 tick 也扣 1），样本在 lab。`sample_collected=false`，`lab_door=open`。
- **公开信息**：初始事故报告说明“样本必须回收、关闭舱门后无法再次开启”；在 hub `R(hull_display)` 给出完整度和泄漏倒计数，在 `X(suit_case)` 显示氧气储量与穿戴方法，在 lab `X(sample_canister)` 说明可拾取；关闭门后不能绕路获取样本。
- **动作**：`X(suit_case)→P(suit)` 解锁并穿戴（需明确从容器露出的时机）；穿戴后可进 lab；`P(sample_canister)` 得 `sample`；`I(lab_door,close)` 为**不可逆**，关后完整度不再减少；`I(pod_regulator,pressurize)` 要求关门；撤离要求样本+安全 pod。
- **参考轨迹**：`M(hub)→M(suit_room)→X(suit_case)→P(suit)→M(hub)→M(lab)→X(sample_canister)→P(sample_canister)→M(hub)→I(lab_door,close)→M(repair_bay)→I(pod_regulator,pressurize)→M(pod)→I(launch,evacuate)`。
- **拒绝／失败**：没有宇航服进 lab 拒绝；先关门再试图拿样本导致“可撤离但任务未完成”（未达 benchmark 胜利）；氧气耗尽前一 tick 提示低氧；不能从关闭门后的公共接口泄露 lab 物品。

### SP-H《黑匣子与双泄漏》：hard

- **剧情与目标**：货舱和实验舱同时失压，实验舱保存黑匣子，货舱里有修复胶；只修一个点无法保证主舱安全。需要制定“收集证据→隔离→修复→撤离”的行动方案。
- **地图**：`bridge↔hub↔suit_room`；`hub↔lab[door_lab]`；`hub↔cargo[door_cargo]`；`hub↔repair_bay↔escape_pod`；`suit_room↔service_duct↔cargo[duct_hatch]`（维修用单向窄道，初始关闭，宇航服可开启）。
- **初始**：`door_lab=open, door_cargo=open, duct_hatch=closed`；lab/cargo 压力=0；`integrity=40`，每个未隔离的泄漏每 tick -1，故开始时每 tick -2；`suit_oxygen=12`，低压区每 tick -1；`blackbox` 在 lab，`sealant` 在 cargo；仪表显示两处泄漏，正确行动需先取黑匣子再封 lab、先取胶再封 cargo。
- **机械与线索**：hub `R(damage_panel)` 公开两个漏点与总损耗速率；suit_room `X(evac_manual)` 说明“关闭隔舱不可重开；可由维修风道短暂进入货舱，风道只有穿着宇航服才能打开”。lab 黑匣子对恢复操作顺序提供非必要记录，不透露 escape 位置。`P(blackbox)`、`P(sealant)` 后可先关对应门，`I(repair_bay,patch_hull)` 消耗 sealant 将剩余漏率归零，`I(pod_regulator,pressurize)` 要求两个门都关、完整度>0。氧气用尽后仍在低压区失败。
- **参考可行计划**：从 bridge 进 suit_room 取 suit，经 hub 入 lab 拿 blackbox，回 hub 关 lab 门；再入 cargo 取 sealant，回 hub 关 cargo 门；去 repair_bay 修复并调压，再到 pod 撤离。此轨迹的**细节操作、初始 integrity 与氧气预算由脚本跑通核验**；如两个泄漏让上述路线数值上来不及，优先把初始 `integrity` 提高到 40（需要 spec 记录），不要暗改泄漏速率。
- **重要策略选择**：也可经 service_duct 取 sealant，但多开一段风道带来时间与氧气成本；是否优于正门由真实计算决定。`blackbox` 遗落虽能人员逃生，但只计 `partial_success`。
- **强制测试**：两个漏点扣血为可加总，关一门只减一份漏率；先关门会永久阻挡对应物品；黑匣子收集后封门是有效解；进入任一低压区扣正确氧气，动态出口 visibility 不泄露隐藏状态；在有效路线成功时不得因同 tick 失压判失败。

## 3. 世界 02｜迷雾灯塔：潮汐、航向与信号

**规则标识**：`tick % period` 控制潮位和雾况；灯台的 `lens_direction`、`lamp_color`、`signal_sequence`、`rescue_window` 是独立状态。潮汐是公开可观察周期，而非隐藏 RNG。信号发射只有在满足观测到的条件时产生救援结果，错误信号不会凭空启动救援。

### LH-E《点亮归航灯》：easy

- **任务**：点亮指向东湾的灯光，在退潮时引导航船靠岸。地图 `keeper_house↔tower_base↔lamp_room`，`tower_base↔east_pier`。对象 keeper_house: `shipping_log`，lamp_room: `lens, beacon_switch, tide_gauge`，east_pier: `signal_flag`。
- **初始**：`tick=0`；潮位 `tide(t)=[HIGH,RISING,LOW,FALLING][t%4]`，灯关、镜头北向；东湾安全信号为镜头 `EAST` + 低潮 `LOW`。
- **公开线索**：`R(shipping_log)`→“救援船将在低潮通过东侧航道”；`X(tide_gauge)` 或初始状态可查当前相位和完整四相循环；`X(lens)` 列出 north/east/west 与可用旋转动作。
- **规则**：在 lamp_room `I(lens,east)`、`I(beacon_switch,on)`；低潮 tick 执行 `I(beacon_switch,send_signal)`（若时机不对，回复当前潮位与等待建议，但**不提供具体未来行动命令**）；在已送达正确信号时到 east_pier `I(signal_flag,board_rescue)` 成功。计时在 action 执行前读取 `tick`，然后推进。
- **参考计划**：读取航海日志→转镜头→点灯→观察潮位／`W` 至 LOW→发信号→到 east_pier 登船。校验周期的定位与信号条件，避免隐藏“奇数回合”谜题。
- **失败测试**：方向不对不会召来救援；高水位信号可重试，错误不永久锁死；`wait` 与 `inspect` 都推动潮位变化。

### LH-M《潮汐双信号》：medium

- **任务**：救援队不认识孤立灯号，需按港务手册先发白光确认，再在高潮窗口发红光引导进港。地图 `keeper_house↔tower_base↔lamp_room`，`tower_base↔signal_gallery`，`tower_base↔dock`。
- **初始**：`tick=0`，潮位周期仍四相；`lamp_color=white, lens_direction=north, signal_sequence=[]`，`fog_density=1`。在 gallery 可查方向扇区，正确方位 WEST。
- **线索**：`R(port_manual)`：明确“白灯确认→红灯靠港，二者不能反序”；`X(route_chart)`：“船从西侧防波堤入港，红灯只在高潮有效”；`R(tide_gauge)` 显示当前潮相和周期。
- **规则**：`I(lens,west)`；`I(lamp,color_white)`、`I(lamp,emit)`（记录 `white`）；切换 `color_red`，仅 `tide=HIGH` 时发红光可完成握手。错误灯色/时相回复 `SIGNAL_NOT_ACKNOWLEDGED`，sequence 的已确认白光不会被悄悄清空（除非超过显式 8 ticks 的有效期；如启用必须提前公告）。到 dock `I(rescue_boat,board)` 胜利。
- **参考计划**：读 manual/chart、将 lens→WEST、白光确认、按 tide gauge 等候 HIGH、红灯确认、去 dock。机制重点是**多阶段握手与时机选择**，不是延长通路。
- **否例**：先红后白不会通过；白光已确认后即使等待也不会导致自相矛盾状态；Wrong direction 不产生确认；救援状态仅在公开 ToolResult 确认后暴露。

### LH-H《迷雾里的三段信标》：hard

- **任务**：浓雾下两条船分别在北礁和西岸寻找灯号。必须读海图判明安全航道，发送三段信号 `SHORT-LONG-SHORT`，并让最后一段落在雾窗打开且潮位允许的时段；确认目标为西岸救援船。
- **地图**：`keeper_house↔archive↔tower_base↔lamp_room`，`tower_base↔west_deck↔dock`，`tower_base↔north_deck`。archive 读 `logbook`，west_deck 查 `channel_marker`，north_deck 查 `reef_warning`。
- **初始**：周期 `fog_clear=(tick%6 in {2,3})`；安全高潮 `tide=(tick%4==0)`；**要求最终第三段仅在两窗口交集时发射**，此交集在 0..11 中只有 tick=8（周期12），之后每12重复；玩家可由 public calendar 计算。初始 `tick=0`，镜头 NORTH，序列空，`attempts=0`。
- **公平线索**：灯室 `R(weather_log)` 显示完整六 tick 雾况周期与四 tick 潮相定义；west_deck `X(channel_marker)` 表明 WEST 可航；north_deck `X(reef_warning)` 表明 NORTH 危险；archive `R(logbook)` 给出三段顺序，同时明确仅**第三段**需在交集窗口，前两段任意时刻有效。
- **操作规则**：`I(lens,west)` 后可 `I(beacon,short/long)`，前三个合法 signal 累积；完成序列前两个动作先确认，第三段若非交集则退回为等待第三段（不要强制重做整个序列），若完全正确则 `rescue_confirmed=true`。错误符号重置当前串并公开显示发生重置；`attempts` 最多 3 次无损序列错误后临时进入 `cooldown=2` 而不是永久死局。`I(rescue_boat,board)` 必须在 dock。
- **参考计划**：依次收集海图和手册信息→设 WEST→发送 SHORT、LONG→在灯室利用 `wait` 对齐 `tick%12==8`→发 SHORT→赴 dock 登船。**先做 BFS 验证是否由于走路/阅读 tick 错过窗口；可等下一轮 tick20。**
- **否例／体验**：错误方向、错误符号和错误时窗分别给不同公开反馈；等待潮窗非随机；不知周期时可在仪表上读到完整规律，禁止只用“现在有雾”让玩家盲等。

## 4. 世界 03｜深海站：压强、进水和取舍

**规则**：使用整数 `water[level]`（0..10）、`pressure[level]`（0..5）、`valves`、`pumps`、`bulkheads`、`spare_capacity`；漏水、抽水、压差均按离散事件计算。`water>=10` 为灾难阈值，`abs(pressure_a-pressure_b)>1` 时强行开门被拒绝（而非瞬间莫名暴毙）。仪表提供可观测水位/压差，不直接读私有全局真值。

### AB-E《止住一舱水》：easy

- **任务**：关闭漏水阀并将通道积水降到安全线，使科研人员进入升降舱。地图 `control↔valve_room↔pump_room↔lift`；`control↔flooded_storage`（非必去支路）。
- **初始**：`water_valve_room=4`，`leak_valve=open`，每 tick +1；`pump=off`；`water>=10` 失败；关闭漏水后水位恒定；每执行一次 `I(pump,cycle)` 水位 -3（下限0），pump 位于 pump_room；lift 可用的安全条件水位≤2。
- **线索**：control `R(flood_console)` 显示流入+1/turn、抽排 -3/cycle；阀门铭牌明示先关漏阀再开泵，lift 灯明确“水位≤2 才可启动”。
- **参考轨迹**：`M(valve_room)→I(leak_valve,close)→M(pump_room)→I(pump,cycle)→M(lift)→I(lift,ascend)`。首次动作和转移每 tick 的水位变化须按 §1.4 时序核对，必要时初始水位 3 而非4，但不能改关阀/抽排的本质。
- **测试**：没关阀也能抽水但下一回合回涨；超水位尝试 lift 拒绝并报当前值；存活通关后不进入失败 tick。

### AB-M《平衡两侧压力》：medium

- **任务**：为转运研究样本打开中间舱门，不能因为压差损坏密封。地图 `control↔west_chamber↔equalizer`，`control↔east_chamber↔equalizer`，`equalizer↔lift[gate]`。west 有 `sample_case`，east 有 `pressure_pump`，equalizer 有 `gate_control` 和双腔仪表。
- **初始**：west=5、east=2（压强整数等级），`gate=closed`，样本未领取；泵一次使 east 压强+1，上限5；要求 `abs(west-east)≤1` 才可 `I(gate,open)`，门开后压力锁定且 lift 可达；无真实时间泄漏（此图重点是压差而非洪水计时）。
- **线索**：`R(pressure_chart)` 会同时报两个测点及阈值差1；`X(sample_case)` 显示须取样本；`I(pressure_pump,raise_east)` 的单次增量公开。
- **参考轨迹**：控制室看图→西舷取样本→东舱泵两次（east=4，差1）→到 equalizer 打开门→进 lift 交样本并上浮。允许泵三次到5，形成可行的不同解。
- **测试**：压差=2 门拒绝而不破门；泵超压被拒绝；样本没拿不能完整成功；两条路线的动机来自规则而非房间深度。

### AB-H《弃舱保核心》：hard

- **任务**：两处同时进水，泵只有一个供电通道，修复总量不足以保住所有舱室。必须保住主控制舱、带走研究数据并安全上浮，可以放弃非关键温室。
- **地图**：`control↔junction↔archive`；`junction↔greenhouse[door_g]`；`junction↔machine_room↔lift`；`machine_room↔ballast`。设备 `junction:door_g / gauge`，`machine_room:pump_router / main_pump`，`archive:data_drive`，`ballast:drain_valve`。
- **初始**：control 水位2、greenhouse 6、machine_room 3；全体每 tick 进水规则：greenhouse+1；若 `door_g=open`，control 每2 tick +1；machine_room 每3 tick +1。`pump_router` 初始 `greenhouse`，每 `pump_cycle` 只对当前选择舱室 -3；泵最多 3 次（能量3），`door_g=open`。当 control 或 machine_room 水位≥10 失败，温室达到10仅标记失守不直接失败。
- **公开证据**：开局 `R(damage_report)` 告知主控和机房是硬约束，“温室可弃保住核心”，路由一次只能为一个水泵供电，能量 3；`archive` 有要带走的数据盘；`junction` 的门关后可切断温室向 control 的溢流（关门前应确认没有必须回收的温室人员，初始报告明确无人）。
- **互动**：`I(door_g,close)` 停止 control 的周期渗水；`I(pump_router,control|machine|greenhouse)` 切换目的地；`I(main_pump,cycle)` 消耗一次能量并对指定舱水位-3；上浮需数据盘、control<6、machine_room<6、门已隔离。场景出现能量分配取舍，不要求把所有水位清零。
- **参考计划**：先去 archive 拿数据盘，关 greenhouse 门，根据公开水位决定至少对 machine_room 抽一次；把剩余泵能给 control／machine 保证均<6，进 lift 上浮。**必须穷举 3 能量分配与行动耗时验证**，若存在因 tick 约束导致不可行，调大容灾水位但不去掉弃舱选择。
- **否例**：全力抽 greenhouse 造成主控失守；未关闭 green 门即使抽了主控后续继续回涨；数据未带走只能计低等级撤离不算主胜利；副舱失守不触发全局失败。

## 5. 世界 04｜极地科考站：寒冷、生存与后勤

**规则**：`body_heat` 0..10、`heater_fuel` 整数、`weather_phase` 周期、`shelter_warm`、`samples`、`team_rescued`。仅在标注 `outdoor=true` 房间的有效回合扣热量：晴朗 -1/turn，暴雪 -2/turn；室内 `I(heater,rest)` 消耗 1 燃料并恢复 4 点（上限 10）。热量≤0 失败；对天气、室内外、燃料和热量先公开再扣。不要用“越走越冷”的叙事代替精确状态。

### PO-E《暴风雪前的避难所》：easy

- **任务**：从前哨站沿雪路抵达应急棚屋，将紧急通讯开通。地图 `station↔snow_pass(outdoor)↔shelter`，`station↔observatory`（可选）。对象 `station:weather_radio,heater`，`shelter:radio_antenna`。
- **初始**：体热10，燃料2，`weather_phase=clear` 且周期 `clear,clear,storm,storm`，棚屋通讯离线；`snow_pass` 扣热量，房间内操作不扣热。
- **线索**：气象台广播明确四回合周期和当前相位，标注室外每行动冷量、棚屋可供暖；`X(radio_antenna)` 提示连接 `I(antenna,activate)` 即可报平安。
- **参考**：先查气象台，选择直接越过 `snow_pass`，到 shelter 激活天线；若遇暴雪，可返回 station 先使用 heater 等待合适窗口。条件是完成通讯且体热>0。
- **测试**：暴雪同 tick 的扣热量统一；heater 消耗燃料且只允许室内；没有凭空死亡／恢复；无需携带无关物件。

### PO-M《燃料还是样本》：medium

- **任务**：必须把冰芯样本带到气象站发报，但燃料只有 2 份，一份可以加热补给站，另一份可给雪地车预热。玩家要取舍行走风险与运输方案。
- **地图**：`station↔supply_hut↔ice_field(outdoor)↔drill_site(outdoor)`；`supply_hut↔vehicle_pad↔station`；`drill_site↔return_route(outdoor)↔station`。关键实体 `drill_site:ice_core`，`supply_hut:heater`，`vehicle_pad:snowmobile`，`station:sample_receiver`。
- **初始**：体热10、fuel=2、clear/storm 两两交替（可观察）；`ice_core` 未取、snowmobile 未预热。徒步路线消耗室外体热；预热雪地车耗燃料1，使 `I(snowmobile,ride_to_drill)` 直接将位置从 vehicle_pad 到 drill_site（1 tick，并在公共结果中明确不经过 ice_field），车辆返回同理；骑行不会隐式复充燃料。
- **线索**：补给日志明确两条方案与车辆耗油；冰芯数据收发器说明必须带回原样样本；体热和燃料始终可查。车只能从指定停靠点驾驶，不能任意瞬移。
- **参考方案 A**：从 station→vehicle_pad，耗 1 燃料预热雪地车→抵达 drill_site→检查并领取 ice_core→乘车回 vehicle_pad→到 station 交付。方案 B 可步行＋供暖，但需检验体热余量且耗时更高。
- **测试**：车的捷径不是无条件传送；样本携带确认前不可交付；燃料耗尽只能走有物理连通的路径；天气同 tick 被记录。

### PO-H《双队员撤离路线》：hard

- **任务**：暴风雪将至，两名队员分别困在钻探站和气象哨位；既要营救双方，又需保证主站最低取暖燃料储备 1。不是单人跑地图，而是动态后勤分配。
- **地图**：`base↔heated_hut↔drill_camp(outdoor)`；`base↔ridge(outdoor)↔weather_post(outdoor)`；`heated_hut↔ridge(outdoor)[rope_bridge=secured]`。实体 `base:control_board/fuel_depot`，`heated_hut:heater/rope_kit`，`drill_camp:researcher_a`，`weather_post:researcher_b`。
- **初始**：玩家体热=10，燃料=4；A、B 初始在 shelter，单独不会因玩家每行动永久失温（避免玩家未知计时导致先天不可解）；天气6回合一轮：前3 clear 后3 storm；绳桥尚未固定；随行队员人数≤1，队员在户外与玩家共享保暖策略；队员若被带回 base 则 `rescued=true`。
- **公开证据**：指挥板显示两名队员所在方位、暴雪预报、必须保留1燃料；`X(rope_kit)` 给出可在 heated_hut 固定 `rope_bridge` 形成快捷连通边；`I(heater,rest)` 耗1燃料；`I(researcher_a|b,escort)` 开始护送（一次最多一人）；带人进入 base 则确认回站。
- **机制**：玩家需要安排先救谁、在哪里补温、是否花行动固定捷径，并让燃料余量≥1。硬失败为玩家冻伤或护送者在户外热量降至0（同行热量从6开始，室内恢复）。避免设置比参考路线还短的不可预知暴雪锁死；首次原型须使用模拟器穷举。
- **参考思路**：先取 rope_kit 并固定绳桥；依天气先完成较远一人的护送到 base，再通过 heated_hut 供暖、完成另一人接回；保证最后燃料≥1。具体步骤和燃料安排由脚本提供**可执行**的 `oracle_plan`，每次进入／离开 outdoor 的热量检查都有数值断言。
- **失败测试**：一次护送两人拒绝；消耗至零燃料即使人救齐也不是完整任务成功；绳桥未固定不可用；天气更新不与玩家 API 延迟相关。

## 6. 世界 05｜沙漠金字塔：线索推理与机关组合

**规则**：地图通路配合线索可达性，`clues_seen`（仅已公开发现的线索 ID）、`lock_answer` 私有、`wrong_submissions`、`trap_state`、`door_state`；符号机关的答案是**确定性的逻辑约束解**，**错误答案统一反馈**“组合未匹配”而不是逐位提示。除必要的剧情，关键 clues 至少在两个不同实体上，检验跨地点记忆。

### PY-E《日轮开门》：easy

- **任务**：识别太阳升起的方位，打开石门取得地图卷轴。地图 `entrance↔mural_room↔sun_door[locked]↔archive`。对象 mural_room:`east_mural`；sun_door:`sun_dial,stone_lock`。
- **线索**：`X(east_mural)` 明确“守门日轮迎旭日，方位为 EAST”；`X(sun_dial)` 提供三个可选方位 `NORTH/EAST/WEST`，没有额外密码。
- **初始**：石门关闭，陷阱0，`roll_collected=false`。`I(sun_dial,east)` 设置朝向；`I(stone_lock,open)` 朝向正确时开门，错误时只返回 `SYMBOL_MISMATCH` 并消耗1 tick；在 archive 拿 `map_scroll` 后 `I(archive_gate,exit)` 胜利。
- **参考**：读壁画→转日轮 EAST→开门→取卷轴→离开。测试不查观测前强行输入是否能偶然过关：允许猜测是游戏机制，但**正确答案必须公开可推导**，错误不可反向泄露答案。

### PY-M《三碑相证》：medium

- **任务**：三个墓室各有一部分刻文；排列三种符号（SUN、MOON、STAR）开启机关。地图 `entrance↔crossroad`，`crossroad↔sun_hall`、`crossroad↔moon_hall`、`crossroad↔star_hall`、`crossroad↔gate[locked]↔treasury`。
- **公开线索**：SUN 石碑“太阳不在最后”；MOON 石碑“月亮紧跟太阳之后”；STAR 石碑“星辰不是第一”；锁的 `X(triple_lock)` 明示**三符号恰好各用一次**。三条约束唯一满足 `SUN-MOON-STAR`（请 Luna 使用 6 排列枚举测试）。
- **机制**：收集三条线索没有特定顺序；`Q(triple_lock,"SUN-MOON-STAR")` 正确则开 gate。错误提交累计 `wrong_submissions`，第3次及以后暂停2 tick，仍可恢复；不要用逐字符提示；treasury 中 `P(royal_tablet)` 与出口完成。
- **参考**：分别检查三块碑→回 crossroad→提交唯一序列→入 treasury 拿目标物离开。
- **测试**：任何两碑不足以逻辑唯一推出答案（如发现有两碑已唯一，需修改线索保留三处证据的价值）；穷举所有排列仅一个解；gate 关闭时不能从别的世界路径进入 treasury。

### PY-H《四符文审判》：hard

- **任务**：四个机关按唯一顺序设置，墓穴有三次安全试错额度。需要组合分散在多处的关系线索，而不是找到一张写着答案的纸。
- **地图**：`entrance↔atrium`；`atrium↔sun_gallery`、`atrium↔scarab_pit`、`atrium↔reed_library`、`atrium↔eye_shrine`、`atrium↔judgment_gate[locked]↔relic_vault`。其中 scarab_pit 进入前须先 `I(bridge,secure)`，桥的操作方法由 atrium 可查；这是一项行动规划，不是猜码。
- **私有谜底（不可显示给 Agent）**：`SUN-SCARAB-REED-EYE`。
- **四条逐一可见、且各自必要的线索**：sun_gallery“太阳先于圣甲虫”；scarab_pit“太阳与圣甲虫紧邻，但不透露谁先谁后”；reed_library“太阳先于芦苇”；eye_shrine“芦苇紧挨着荷鲁斯之眼之前”。每个符号必须恰好使用一次；四条约束交集唯一为 `SUN-SCARAB-REED-EYE`。四条线索中**任意去掉一条都会剩下不止一个候选排列**（可用 24 排列枚举验证），因此四房都有实质调查价值。
- **初始**：`wrong_submissions=0`，锁 `sealed`，机关触发后 `trap_pressure` 累计+1，达到3进入 `cooldown=3` 且公告“机关暂时锁定”，而不是造成永久不可解。正确解并已检查过四个线索实体时开门（若要求查看四实体，必须在任务目标与门铭文上事先公开；不应隐藏强制打卡）。
- **新玩法**：玩家可规划拜访顺序和解题顺序；进入 scarab_pit 的桥可以绕回，失败时不强制回初始点。`Q(judgment_gate,answer)` 是推理提交，不允许读取 private answer 的候选提示。
- **参考**：atrium 查看门规→依次收集 sun/scarab/reed/eye 的约束（先固定桥）→得出 SUN-SCARAB-REED-EYE→提交→入 relic_vault 拿 `seal_relic`→回出口成功。
- **否例**：未固定桥不能过 pit；错误排列统一反馈；3 次失误后能等待恢复；同一固定规则 seed 间答案不变，未来变体须以定义 hash 隔离。

## 7. 世界 06｜废弃地铁：离散事件列车调度

**规则**：每辆列车有 `location`, `status=held/ready/moving/arrived`、`reserved_segment`；道岔有状态，单线区段同时容纳最多一列车。**主要互动是信号、道岔、车辆动作**，不是开电箱。时间由回合驱动。下文规定一个简化且测试友好的调度抽象：

- `I(train_x,advance)`：该列车沿其当前公开合法路由移动一个区段，成功占用新区段并释放旧区段；如果下一段有人占用/未授权/道岔错误，拒绝并报告冲突，不暗中穿模。每辆列车仅在 Agent 下令时移动；`wait` 不自动让车前进，以保证清晰可验证的决策权。
- `I(switch,west/east/...)`：配置道岔；`I(signal_x,green/red)`：配置许可信号；信号有效期和权限要明确。
- 初期用**离散可观测调度**而不加入列车自动运动。可增加可选时限，但不能让模型因多次 `inspect` 丢失不可知的时机。对每个移动操作检查区段互斥与站台容量。

### SU-E《最后一班车》：easy

- **任务**：将停在仓库的 1 号车安全送往北站台。地图是轨道网络而非玩家步行房间：`depot—junction—north_platform`、`junction—closed_siding`。玩家控制位置 `control_room`，可访问 `switch_j,signal_1,board_1`，无需四处步行。
- **初始**：train1 在 depot，switch_j=SIDING（错误线），signal1=RED，north_platform 空。操作选择通过 `X(track_map)` 与 `X(board_1)` 展示完整局部状态。
- **公开规则**：图表显示正确方向 NORTH、绿灯才能发车；一次 advance 一条边，错误道岔下车会进入岔道但可调回（不得无理由瞬间失败）。
- **参考**：`I(switch_j,north)→I(signal_1,green)→I(train_1,advance)`（depot→junction）→`I(train_1,advance)`（junction→north_platform）；列车到站胜利。
- **测试**：红灯阻发；switch 不对时可发生可解释的岔道偏离且能恢复；禁止瞬移两段；历史轨道占用记录清晰。

### SU-M《会车与道岔》：medium

- **任务**：两列车共享站前单线，须依次通过，任何时刻不能同时占用 `single_track`。地图：`depot_a→single_track→platform_a`，`depot_b→single_track→platform_b`，道岔由控制台指定出口 `A/B`；列车一旦入单线直到下一次 advance 才释放它。
- **初始**：train_a@depot_a，train_b@depot_b，single_track 空，`route_switch=A`，两信号 RED；到站条件两车各自到自己的 platform。
- **线索**：`R(dispatch_log)` 写明“单线最多一车，先清出占用再放第二车；A 向北、B 向南”；当前区段占用仪表实时公开。
- **参考**：设 route=A→signal_a GREEN→advance A 入单线→advance A 到 platform_a（释放单线）→设 route=B→signal_b GREEN→advance B 入单线→advance B 到 platform_b。两车到站成功。允许 B 优先，也是正确策略。
- **测试**：A 在单线时 B advance 必然 `TRACK_OCCUPIED` 且 B 位置不变；signal RED 禁止；A 已达站后可合法清空占用；不能将一个车调至错误站台仍算成功。

### SU-H《三车共享干线》：hard

- **任务**：紧急疏散时三列车 A/B/C 要在 18 个控制 tick 内到达各自站台；共享干线最多占一车，并有一个可暂存列车的避让侧线。目标是安排顺序避免死锁，并满足优先救护车 A 必须先于 C 到站。
- **轨道**：`depot_a→trunk→platform_a`、`depot_b→trunk→platform_b`、`depot_c→trunk→platform_c`；`trunk↔siding` 是能容纳一车的侧线（通过 `I(switch_trunk,siding)` 配置）。玩家控制室可远控所有信号／switch。
- **初始**：A/B/C 在各 depot，trunk 空，siding 空，3 signals RED，`switch_trunk=A`，`deadline=18`（从初始 tick 开始所有 Action 计时）。`platform_a/b/c` 各容量1；全部到站前存在下一次 tick 将超过18时提前播报。
- **公开规则**：调度板说明每个 train advance 使车走一条区段并占用，到站需正确 route；切 switch 和改信号均耗 tick；所有区段冲突是硬规则，最后期限是评测预算（18 可能需经过 oracle 证明足够，如果纯控制操作超过预算，应提高到 24 而非删掉时限）。优先级 A before C 用公开医护调度令说明。
- **推荐可行安排**：一次配置 A 绿灯/route→A 进 trunk→A 到 platform_a；再配置 C 绿灯/route→C 进 trunk→C 到 platform_c；最后 B similarly，确保 A 在 C 之前。**困难特色不应仅“三列车依次发车”**：在 hard 加入 `maintenance_lock`：B 发车后 `route_switch` 暂时锁定到 B，需从公共日志已知在 B 到站后调用 `I(maintenance_switch,release)` 才能改给下一车；另设 `priority_window` 要求 A 必须先于 B 或 C 的最终到站（已公开）。这使 B 优先会造成至少多一个解锁动作，有真实策略差异。
- **参考轨迹**：所有信号初始 RED；为 A 设置 route/绿灯→A 连续 advance 两次；为 C 设置 route/绿灯→C 连续 advance 两次；最后为 B 设置 route/绿灯→B 连续 advance 两次（总计约 12 tick，不超过18）；禁止在 trunk 有车时突然切路由以造成路径瞬变：路由在该车进入 trunk 时锁定为 `reserved_exit`。
- **否例**：两车同进单线不可；B 先启动增加维护锁额外耗时但不构成无根据必死；到站顺序约束不满足时应该报 `PRIORITY_VIOLATION` 或附加低等级评分（主胜利是否要求必须一开始说明）；移动中的车路线不被后续改 switch 追溯篡改。

## 8. 世界 07｜火山观测站：热量控制与灾害临界值

**规则**：核心状态 `heat`（整数）、`coolant_stock`、`loop_a_on/loop_b_on`、`valve_state`、`eruption_clock` 与 `samples_collected`。每个非终局 tick 先应用直接操作，再按 `heat += base_heat - cooling_effect` 更新；热量 ≥ `critical` 才灾难失败。**高温状态和温度变化速率都必须公开**；如果需要冷却资源，必须能从读数算出剩余安全窗口。

### VO-E《冷却第一阀》：easy

- **任务**：阻止温度继续上升并让观测站安全撤离。地图 `control↔cooling_room↔exit_platform`，`control↔viewing_deck`。设备 `control:heat_monitor`，`cooling_room:coolant_valve,main_pump`，exit:`cable_car`。
- **初始**：`heat=4, critical=16, base_heat=+1/tick, main_pump=off, valve=closed, coolant_stock=5`。泵打开且阀 open 后每 tick 提供 -3 冷却（净 -2）；`coolant_stock` 每个有效冷却 tick -1，至少要把 heat 降到≤5 才可通过救援缆车。
- **可见线索**：`R(heat_monitor)` 显示温度、每回合升温、冷却净效果和 critical16；`X(main_pump)` 描述“阀门关闭时水泵空转”；`X(cable_car)` 显示离站需 heat≤5，且泵曾运行成功。
- **参考**：控制室读监测→cooling_room 开阀→开泵→等待直至监测温度≤5→到 exit_platform 启动 cable_car。**初始热量与 action tick 会使温度回到4或更低，参考路径应由 runner 证明。**
- **测试**：只开泵不打开阀门不冷却；coolant 不会为负；升温与降温先后语义固定；critical 恰好等于阈值触发失败。

### VO-M《双回路失衡》：medium

- **任务**：两条热交换回路一条高温、一条低温，单开某一路不足以保障安全；必须调整两个阀的流量比例，在有限冷却剂下达成热平衡。
- **地图**：`control↔junction↔loop_a_room`、`junction↔loop_b_room`、`junction↔service_lift`。设备 `control:dual_monitor`，loop_a:`valve_a`，loop_b:`valve_b`，junction:`pump_switch`。
- **初始**：热源 A=7、B=5；`critical_a=14, critical_b=14`；每 tick 两个温区分别 +1；阀流量只能选 `off/low/high`，整套系统最高 **3 单位流量**；high 净冷却某侧 -3/tick，low -1/tick；实际每 tick 的净增量等于热源+1再减冷却值；冷却剂库存=18流量单位（每 tick 减当前流量总数）。
- **线索**：监测板说明总流量预算3，A 当前比 B 高2，至少要令两温区均≤6且 pump running 以完成安全认证；`X(valve_a/b)` 列出 high=3/low=1 的效果和库存损耗。
- **参考策略**：先给 A high 暂时降温，在合理温度时改为 A low + B low（总流量2），再通过调整确保两温度均≤6；到 service_lift `I(evac,depart)`。**这关允许多解，必须运行规划搜索保证库存足够；若 B 根本无法降到6，则增加 `medium` 强度值为2，而非偷偷降低胜利条件。**
- **否例**：A high+B high 超流量必须拒绝并解释；只冷 A、B 失控造成失败；泵关/阀 open 不产生冷却；耗完库存后热量照常增长。

### VO-H《喷发前的取舍》：hard

- **任务**：喷发前同时需要采集关键温压数据和保护撤离索道；研究目标不能无限拖延，必须决定“先采样还是先稳住热控”。
- **地图**：`command↔cooling_hub↔lava_probe(outdoor)`；`cooling_hub↔aux_tank`；`command↔cable_station[stable_heat]`；`cooling_hub↔vent_room`。实体 command:`seismic_clock`，lava_probe:`core_sample`，aux_tank:`coolant_canister`，cooling_hub:`cooling_router/pump`，vent_room:`vent_flap`。
- **初始**：`heat=6`, `critical=20`, `base_heat=+2/tick`, `coolant=8`, `pump=off`, `vent_flap=closed`; 每个冷却 tick pump 消耗1 coolant、heat -4（和 base_heat 叠加净 -2）；`I(vent_flap,open)` 可降低 `base_heat` 从+2至+1，但走到 vent_room 需要时间。采样 `P(core_sample)` 需要在 lava_probe，必须先 `I(probe_shield,deploy)`，护罩操作耗1tick。
- **公开规则**：`R(seismic_clock)` 明确临界热量、增长速率，`X(pump)` 给消耗/降温值；`X(core_sample)` 提醒需护罩；`X(cable_station)` 表明启动需 heat≤10 且样本已收集，撤离动作即时成功。
- **推荐参考策略**：先去 cooling_hub 激活 pump（开始降低热量），利用 coolants 提供的缓冲时间走 lava_probe 采样，再决定是否通过 vent_room 永久降低热增长，最后返回 command→cable_station 撤离；必要时于 cooling_hub 用 `I(pump,off)` 节省冷却剂。**设计必须要求“提前降温+合理取样”优于盲目冲采样，且可通过脚本模拟证明可解。**
- **失败测试**：冷却剂耗尽后再次开泵不能免费制冷；采样前未放护罩拒绝；走路也加热；在等号边界撤离判定一致；允许错过一次最佳路线后通过 vent_flap 恢复（除非明确进入灾难状态）。

## 9. 世界 08｜丛林遗迹：地标导航与环境地图变化

**核心定位**：不是把出口藏得更远，而是让 Agent 学会**从局部地标重建路径**。`visible_landmarks`、`trail_orientation`、`vine_gate_state`、`weather_phase`、`known_routes` 不直接提供全局地图；标记树／石像的线索都来自当前房间。固定地图必须手工设计方向关系、条件边和导航提示，不能用随机房间名称糊弄“迷路”。

### JU-E《三棵标记树》：easy

- **任务**：在分叉雨林找到古碑并带回记录。地图 `camp↔fork↔red_tree↔ruin`，另 `fork↔blue_tree` 和 `fork↔white_tree`；三个岔路均看得到不同树标。
- **初始**：碑文在 ruin，`notes_collected=false`；没有随机事件或不可逆陷阱。
- **线索**：camp `X(scout_note)`：“红色标记指向石碑，蓝色标记指向溪流，白色标记只通观测点”；fork 的 `Observation` 显示三条命名出口和标记颜色，走错后可立即回头。
- **参考**：看线索→fork→red_tree→ruin→`X(ancient_tablet)`→`P(ruin_notes)`→回 camp→`I(field_report,submit)` 成功。`blue_tree/white_tree` 支路必须有环境叙事与可区分反馈，不能只写“这里什么都没有”。
- **测试**：标记与真实拓扑一致；走错路线不会锁死；没有拿笔记不能上报；地图不直接向 Agent 暴露完整隐藏邻接表。

### JU-M《会转向的藤门》：medium

- **任务**：遗迹入口被活藤覆盖；控制石碑上的转盘能把藤门从北路径改接到东路径。玩家必须观察方向变化并重新定位。
- **地图**：`camp↔fork↔turntable`；`fork↔north_path`、`fork↔east_path`；`north_path↔hidden_ruin[orientation=NORTH]`；`east_path↔hidden_ruin[orientation=EAST]`；`hidden_ruin↔camp[shortcut_unlocked]`。
- **初始**：`orientation=NORTH`, `shortcut_unlocked=false`；从 camp 的公开任务笔记得知目的地在东侧遗迹，但藤门当前指北；turntable 互动允许 `set_north/set_east`。
- **线索**：`X(turntable)` 写明操作改变 **当前可走通的那条连边**；`X(rune_marker)`（在 fork）告知“目标遗迹在 east_path 之后”，不得由世界预定义 phase 直接报 `set_east`。
- **参考**：camp→fork 看方向铭牌→turntable 调为 EAST→返回 fork→east_path→hidden_ruin 取目标→开启 shortcut→回 camp 完成任务。
- **失败测试**：变向后北路径的条件边立刻失效（若玩家已在 hidden_ruin 要保留可返回的一条安全路径，防 softlock）；既有已走轨迹不应在 Trace 中被篡改；`look` 应报告当前可见出口而非未来出口。

### JU-H《风暴重绘路径》：hard

- **任务**：暴雨后两条河道会交替可通行，必须在变化的地图中找到三个古代路标的联系，进入祭台并安全回营。
- **地图**：`camp↔fork↔river_bank`；`fork↔high_ridge↔stone_circle`；`river_bank↔stone_circle[river_low]`；`stone_circle↔altar[marker_aligned]`；`altar↔return_pass↔camp[return_gate_open]`。
- **状态／周期**：`storm_phase = tick%6`，其中 0,1,2 为低水位、3,4,5 为涨水；低水可走 river_bank↔stone_circle，高水时河道封闭但 high_ridge 永远可通。`marker_aligned=false`，`return_gate_open=false`。
- **线索**：camp `R(weather_log)` 公开六相周期和可预测水位；fork `X(path_sign)` 标注山脊全年可走、河道仅低水；stone_circle `X(three_stones)` 得出按 `OAK→FERN→VINE` 次序触碰才开 altar 门（线索由三块不同石上图案组合，图案内容要分别放在 fork/river_bank/high_ridge，不能只在祭台直给答案）。
- **动作**：`I(stone_circle,oak/fern/vine)` 逐步记三段有效序列；错误触碰清空但可重试。完成后解锁 altar；在 altar `P(relic_seed)` 且 `I(return_seal,unfasten)` 解锁返回通道；最终回 camp 上报。水位变化时，**已进入河道的玩家不能停在不存在的节点**，仅在离开／进入受影响连接时检查条件。
- **参考**：先收集三处地标信息，按天气选择河道或稳定山脊抵达 stone_circle，输入 OAK/FERN/VINE，入 altar 取 relic，开返程门，从 return_pass 安全回营。多路线可解，不能要求固定步数。
- **否例**：涨水拒绝通行河道并给当前可见水位，绝不永久锁死；序列错误可恢复且无答题字符泄漏；完成后返程门逻辑闭合；强天气不应让游戏在任意回合完全无可行路径。

## 10. 世界 09｜月球基地：舱外氧气与日照能源预算

**世界特征**：以“出去之后**能否安全返回**”为主要规划难题。`suit_o2`, `reserve_o2`, `battery`, `solar_exposure`, `airlock_state`, `eva_payload`。氧气仅在 `outdoor` 区域行动时下降，含进入室外的移动 tick；重新进室内补给舱即可停止损耗；`I(refill_station,refill)` 仅在充氧站生效且消耗库存。所有出舱前均可查余量、目标距离与风险；不使用宇航服不能穿过气闸。

### LU-E《第一趟舱外行走》：easy

- **任务**：出舱修好太阳能板，安全返回基地。地图 `habitat↔airlock↔solar_pad(outdoor)`，`airlock↔storage`；工具 storage:`patch_kit`；设备 airlock:`suit_rack`, solar_pad:`broken_panel`。
- **初始**：宇航服充氧10，patch_kit 在 storage，面板损坏，airlock=closed；穿戴后 `I(airlock,cycle_out)` 开通室外边，返航需 `I(airlock,cycle_in)`，成功条件 panel_repaired 且人位于 habitat 且 suit_o2>0。
- **线索**：suit rack 仪表可见氧气10，每个室外有效 tick -1；`X(broken_panel)` 写明需 `patch_kit`；storage 公开物品，不知道维修包不能凭空使用。
- **参考**：storage 拿 patch_kit→穿宇航服→循环出舱→solar_pad `U(patch_kit,broken_panel)`→回气闸→循环入舱→habitat 成功。
- **测试**：没有 suit 不可出舱，氧气不能负数，“已修好但人没回来”不算成功，修复工具只在持有时有效。

### LU-M《日照与电池》：medium

- **任务**：必须在日照窗口给备用电池充电，再到舱外通信塔更换模块；不能把任务误解成“找电池即可”。
- **地图**：`habitat↔power_room↔airlock`；`airlock↔solar_array(outdoor)`；`airlock↔antenna(outdoor)`。物品 power_room:`battery_module`，设备 solar_array:`solar_charger`，antenna:`comms_socket`，habitat:`o2_station`。
- **初始**：电池能量0，充电需求3；日照周期 `sunlit=(tick%6 in {0,1,2})`，阴影3,4,5；宇航服 O2=12，基地预备氧气池6，每次 refill 最多+6且消耗相同 reserve 数量（上限 suit O2=12）。
- **线索**：基地屏幕提前公开六回合周期；`X(solar_charger)` 写明需已持有 battery_module、日照时每 `I(solar_charger,charge)` 充1单位；`X(comms_socket)` 写明需电量≥3；允许在室内 `W` 等日照窗口。
- **参考**：取 battery→穿 suit→到 solar_array 按公开相位充三次（必要时等下一次日照）→返回 airlock／基地充氧→到 antenna 装 battery→回 habitat 完成通讯确认。**因在太阳能阵列 `W` 也耗氧，必须模拟验证氧气够用；不够则增加初始 reserve 而不是暗改耗氧。**
- **否例**：阴影充电拒绝并报相位；无电 battery 不能修 antenna；O2 余量不足出发提示危险但不作弊拦截所有风险；复充消耗 reserve。

### LU-H《双 EVA 救援》：hard

- **任务**：一名队员困在远侧中继点，还需修复信号桅杆才能导航回舱；两趟舱外任务争用氧气和电池，必须安排返程安全储备。
- **地图**：`habitat↔supply↔airlock`；`airlock↔relay_point(outdoor)`；`airlock↔mast(outdoor)`；`relay_point↔crater_rim(outdoor)↔mast(outdoor)`（长线捷径，但氧气负担高）。对象 `supply:o2_station,charged_cell`，`relay_point:astronaut_b,locator`，`mast:signal_mast`。
- **初始**：suit_o2=12、reserve_o2=10、battery_cell=1，mast_offline、astronaut_b=waiting，`astronaut_b_suit_o2=5`（仅在被护送时消耗每 outdoor tick 1），solar 窗六相；开始时小队员在安全应急棚内不会因全球 tick 静默掉氧。`charged_cell` 必须从 supply 取，只有一次；太阳能 charger 可在 mast 的维修盒中按太阳窗口给 spare_cell 充电，但不是必需路线。
- **机制／线索**：`R(rescue_plan)` 明确“先恢复 mast 才能安全定位被困队员返回；每人穿室外时按 tick 减氧；两人不能共享同一宇航服氧气”，`X(signal_mast)` 显示需一个 `charged_cell` 且可在本地修；`I(astronaut_b,escort)` 后队员跟随同路往 airlock，安全返航后回 habitat；可在 airlock 为自己补氧，队员只在 relay_point 有应急补氧一次 +3。
- **参考策略**：首趟取 cell 出舱维修 mast→回 airlock 充氧；第二趟前往 relay_point，确认队员初始氧气/应急补氧→escort 沿最短路线带回→完成 habitat check-in。另一策略可在同趟串联两任务，但应在部分天气窗口因氧气不划算。**严格验证随行队员氧气与返航动作数，保证至少一条合法行动轨迹。**
- **否例**：mast 未恢复就护送入舱不算完整任务；单次低氧直冲不能永远无代价；队员不在当前 room 无法远程 escort；无限 refill 不允许；需要回程，而非触发救人旗标就通关。

## 11. 世界 10｜古堡谜案：对话、证据与唯一推理结论

**规则**：世界中有可观察 NPC、证词与物证；`dialogue_topics` 通过 NPC 当前 `inspect` 公开列出；`I(npc,topic)` 获取具体陈述且消耗1 tick，`evidence_found` 只从实际 `inspect`/`pickup` 成功事件更新。最终 `submit` 是**陈述一个事实结论**，不是打开密码终端。真相存 private definition，NPC 不“知道玩家无从看到的真实答案”。不可制造纯主观无标准答案的侦探谜题。

### CA-E《看门人的两句话》：easy

- **任务**：找到失踪的档案钥匙，打开古堡书房；通过问话决定该去哪个房间。
- **地图**：`great_hall↔gatehouse`、`great_hall↔kitchen`、`great_hall↔library[locked]`；kitchen↔pantry。NPC gatehouse:`gatekeeper`，厨房:`cook`，pantry:`key_box`。
- **初始**：library 关闭，`archive_key` 在 pantry 的 key_box；门卫说“我在厨房交还钥匙”，厨师说“交还后放进储藏室蓝色盒子”，均是诚实可验证的叙述。
- **公开可选话题**：`X(gatekeeper)`→`I(gatekeeper,where_key)`；`X(cook)`→`I(cook,where_stored)`；`X(key_box)`→揭示 `archive_key`。玩家从 NPC 得到下一处调查方向，但最终物品仍须实际回收。
- **参考**：问门卫→问厨师→pantry 看盒→取 key→回 library `U(archive_key,library_door)`→`I(archive_desk,register)` 胜利。
- **否例**：未见钥匙就 pickup 拒绝；没有钥匙不准开 library；NPC 重问只返回同一既定证词，不靠随机改口制造剧情。

### CA-M《午夜证词》：medium

- **任务**：确认谁在午夜前转移过封印档案，找到藏匿书卷，而不是随意指认一个 NPC。
- **地图**：`hall↔watchtower`、`hall↔courtyard`、`hall↔infirmary`、`hall↔records_room`、`records_room↔secret_study[locked]`。NPC `watchtower:guard`, `courtyard:caretaker`, `infirmary:physician`。证据 `records_room:access_log / clock_report`。
- **真值**：管事 caretaker 曾在 23:50 到 records_room 转移书卷、藏在 secret_study。守卫称当时自己在 watchtower，医师有病历记录确证在 infirmary；caretaker 声称一直在 courtyard。
- **线索**：`R(access_log)`：“23:50 records_room 开门者用 caretaker badge”；`X(clock_report)`：“门禁时钟已由钟楼校准，误差≤1分钟”；`I(caretaker,where_were_you)` 得错误的不在场陈述；`I(guard,night_patrol)` 证实午夜前 caretaker 从记录室方向走出；`X(secret_study_door)` 可见管理员 badge 可解锁。
- **提交格式**：`Q(case_board,"CARETAKER")` 只接受在玩家已公开发现 access_log 和至少一条独立证词／校验线索之后；成功后 `I(secret_study_door,open)`，入密室取书卷，回 hall `I(case_board,close_case)` 通关。**若不要求证据收集先决条件，必须把“猜中答案但没有调查”的情况标记为 lucky_guess，而非等价推理成功。**
- **参考**：询问 caretaker、查门禁日志和校准报告、找 guard 交叉核对→唯一归属 caretaker→提交→取卷→结案。
- **否例**：单凭嫌疑人名字错误提交不回显“差一个字”；两个无罪 NPC 的时间线不能同时与真值冲突；门禁记录与证词的关系是逻辑可验证而非剧情强行指定。

### CA-H《谁篡改了封印》：hard

- **任务**：王室封印在 21:00—21:05 间被篡改。三名嫌疑人 steward MARIUS、守卫 GARETH、医师 ELISE；玩家需指出唯一作案人，并提交两项支持结论的证据。
- **地图**：`grand_hall↔key_archive`、`grand_hall↔seal_chamber`、`grand_hall↔watch_post`、`grand_hall↔infirmary`、`grand_hall↔servant_quarters`；`key_archive↔secret_passage[unlocked_by_evidence]↔seal_chamber`。NPC servant_quarters:`marius`，watch_post:`gareth`，infirmary:`elise`。
- **隐藏真相**：MARIUS 在 20:50 领取唯一可开封印柜的青铜钥匙，21:00—21:05 在 seal_chamber 修改封蜡，21:10 归还钥匙；GARETH 和 ELISE 分别有独立互证的不在场证据。Marius 声称“我当晚从未碰过钥匙”。
- **关键公开物证**：`R(key_ledger)`：“20:50 MARIUS 取钥匙、21:10 MARIUS 归还”；`X(seal_wax)`：“新封蜡残留与管事办公用的蓝蜡一致”；`R(door_record)`：“封印柜仅持这把钥匙可开，篡改发生在 21:00—21:05”；`R(guard_roster)`：“GARETH 在 20:45—21:15 看守南门，另有见证签名”；`R(medical_chart)`：“ELISE 20:40—21:15 在医务室连续救治，有两名患者签名”。
- **证词**：`I(marius,key_access)` 得“我今晚从没取过钥匙”；`I(gareth,where_were_you)` 得与 roster 一致陈述；`I(elise,where_were_you)` 得与 chart 一致陈述。NPC 证词不能随机串改。
- **操作**：玩家至少发现 `key_ledger` + `seal_wax` + `door_record`，并调查另两人至少一种独立排除证据后，`Q(verdict_desk,"MARIUS|KEY_LEDGER+SEAL_WAX")` 才能获完整胜利。格式不需用户从 prompt 生造：`X(verdict_desk)` 公告 `SUSPECT|EVIDENCE_A+EVIDENCE_B`，并显示可提交的已收集 evidence ID；错误答案或缺证据只回复“证据链不充分/结论不一致”，不给出正确人名。允许更多完整证据组合，但应写到显式校验规则，不逐字硬编码唯一解路径。
- **秘密通路**：查明钥匙归属并发现守卫手稿可解锁 shortcut，提升调查效率，**不允许**经 secret_passage 直接绕开核心证据判胜。
- **参考**：查 door_record→key_ledger→seal_wax；盘问 Marius 并通过 guard_roster/medical_chart 交叉排除 GARETH/ELISE→按已公开格式提交 MARIUS + 两条证据→胜利。
- **机器可证明项**：对三嫌疑人归属做事实约束枚举，只有 MARIUS 同时匹配 access/time/material/alibi；无证据胡乱提交不得在推理评价上记为“完整成功”；任务有确定、可解释的唯一标准答案。

### 12.2 状态、反馈与展示字段的公共 Schema（概念样例）

下述 JSON 仅展示 **V3 新格式**的结构，不代表旧 `WorldState` 已存在这些字段。具体 Pydantic model 由 Luna 在 spec 确认，严禁将 `hidden_truth` 整包暴露给模型。

```json
{
  "world_version": "pyramid-escape-world-v3-hard-zh",
  "scenario_id": "PY-H",
  "family": "pyramid",
  "difficulty": "hard",
  "public_goal": "依据四处符文碑的规则解开审判之门，带走封印之物。",
  "ruleset_version": "pyramid_rules_v3.1",
  "clock": {"tick": 0, "tick_policy": "all_validated_environment_actions"},
  "public_initial": {
    "current_room": "entrance",
    "visible_objects": ["welcome_inscription"],
    "available_exits": ["atrium"],
    "public_status": [{"id": "gate", "value": "sealed"}]
  },
  "private_initial": {
    "symbol_answer": "SUN-SCARAB-REED-EYE",
    "wrong_submissions": 0
  },
  "success": {
    "conditions": ["seal_relic_in_inventory", "returned_to_exit"],
    "score_fields": ["wrong_submissions", "executed_actions", "clues_inspected"]
  }
}
```

**安全要求**：private 仅可在 Env 构造、rule implementation 和 test oracle 访问；`Observation`、Agent prompt、候选动作 `available_interactions` 只含根据当前位置/已公开线索计算的事实。比如允许公布 `submit` 接受 `SUN/MOON/STAR` 三种符号；不得公布正确排列。

### 12.3 增强 ToolResult 原因，但保持旧数据兼容

保留现有 `ToolReason` 的值。新值可按机制分组追加，如：

- 压力／安全：`LOW_PRESSURE`、`BULKHEAD_CLOSED`、`PRESSURE_UNSTABLE`、`OXYGEN_DEPLETED`、`ROOM_FLOODED`、`PRESSURE_MISMATCH`；
- 动态窗口：`SIGNAL_NOT_ACKNOWLEDGED`、`TIDE_UNSAFE`、`STORM_WINDOW`、`SOLAR_UNAVAILABLE`；
- 调度／设备：`TRACK_OCCUPIED`、`SIGNAL_RED`、`SWITCH_MISMATCH`、`FLOW_LIMIT`、`RESOURCE_EXHAUSTED`；
- 推理／交互：`SYMBOL_MISMATCH`、`EVIDENCE_MISSING`、`VERDICT_REJECTED`、`DIALOGUE_AVAILABLE`、`CHOICE_NOT_AVAILABLE`；
- 成功：沿用通用 `ESCAPED` 的**legacy 语义**；V3 建议增加 `SCENARIO_COMPLETED`，不能把金字塔解谜、地铁调度、古堡破案全部硬标为“逃生成功”。

**拒绝反馈不应输出私有真值**：例如不能说“正确符号是 SUN-SCARAB-REED-EYE”，只能说“顺序不符合石碑的约束；已提交的组合未生效”。失败反馈可以引用已经公开的约束 ID 而非正确答案。

### 12.4 同一 Action grammar，世界允许各有可选操作

- `look`、`inspect`、`move` 在所有地图可用；特定机制按可见实体决定 `use/interact/submit` 合法性；`wait` 在任何时间世界可用，在无动态进展的静态关卡可拒绝或消耗回合并明确提醒。
- `available_interactions` 不用全世界候选字典。只能包含当前 room 可见目标及必要的合法操作词（例如 switch 的 `north/south`），不能把隐藏角色、未来地点、陷阱答案传给 Agent。
- Strict JSON schema 的 `oneOf/anyOf`、全部 required 字段、`additionalProperties:false` 与 OpenAI-compatible gateway 兼容需独立测试。若某网关不支持复杂 schema，选择显式版本化的退化 contract，不能静默把 Action 解析成自由文本且改变实验定义。
- Fake provider 不应依赖 hardcoded 世界正确答案作为 Agent 策略；允许**测试专用 oracle**驱动环境，Fake baseline 只是接线验证，与模型能力评价完全隔离。

### 12.5 失败终止与多结局处理

- `SCENARIO_SUCCESS`：完成该关**主目标**，且满足规定安全条件。
- `PARTIAL_SUCCESS`：人员逃生但关键目标丢失，或者完成调度但违反非安全奖励项；由关卡私有判据明确，**Benchmark 的主成功率不把 partial 计作完整成功**。
- `SCENARIO_FAILURE`：进入不可恢复终态，如氧气耗尽、关键主舱被淹、火山过热。应当能够说明哪个公开指标越过阈值。
- `STEP_LIMIT`：外部预算耗尽但世界本身尚未失败；与 scenario failure 区分。
- `PROVIDER_ERROR`：模型接口失败导致中断；不改写成世界失败。
- 在新 Trace 中写 `scenario_id`、`scenario_event`、`scenario_status`、`failure_reason`、`score_components`，全部是非敏感公开或安全评估字段。旧 Trace 缺少时按 absent 处理，不反向推定失败理由。

### 13.1 防止再次批量换皮的“玩法多样性”实质门槛

对每个家族要求做到：

1. **核心胜利谓词不同**：不能全部检测 `authorization_code_read && escaped`。例如地铁判所有列车到站；古堡判有证据链的正确结案；金字塔判符文逻辑与道具带出。
2. **至少一个世界独有的状态转移**：飞船隔舱连边受压差影响、灯塔周期信号握手、深海抽排分流、极地天气体热、金字塔组合约束、地铁区段互斥、火山冷却流量、丛林可变地形、月球 EVA 返航余量、古堡证词一致性。
3. **失败来源与该世界的机制相关**：不能 30 关全部只可能 `WRONG_TARGET` 与 `STEP_LIMIT`；至少支持上表的主题特有拒绝／失败。
4. **三档难度递进的是规则耦合**：easy 单机制，medium 交互，hard 因果与策略取舍；不强求固定房间数、不把房间数量当难度定义。
5. **剧情描述与真正规则一致**：写“持续漏水”必须真的按 tick 进水；写“雷暴窗口”必须真的改变可操作时机；写“NCP 证词”必须能通过 `interact` 获取并核对。虚假的装饰性描写记作设计缺陷。
6. **必须有非线性的后果／规划选择**：如先关门会丢证据、先发某列车会锁路线、先分配冷却流量会改变热态。至少大多数 medium/hard 关卡具备两个以上有逻辑意义的路径或策略。

### 13.2 手工质量评分（逐关，非模型考试）

每项 0/1/2 分，总分 12，**每关 ≥10 分才算内容设计验收**。此评分属于策划审核，不伪装成科学量表。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 玩法独特性 | 仍是通用修电读码 | 仅局部独特 | 核心规则与同组其他世界不同 |
| 状态因果性 | 文本装饰 | 规则触发有限 | 状态转移决定操作效果与结果 |
| 信息公平性 | 关键答案不可知 | 部分需猜 | 关键线索公开、可推导、可追溯 |
| 决策与后果 | 唯一机械路径 | 有可逆分支 | 存在有代价、可解释的不同决策 |
| 难度设计 | 只堆房间与道具 | 单约束增加 | 同主题多机制耦合、逐档深化 |
| 验收完整性 | 不可复现 | 只有参考解 | 正向/逆向/边界/重置/安全均齐 |

至少**三名独立审查视角**（可由不同 LLM 审阅任务或测试模拟，但不得同一个会话自我给高分后直接通过）：规则一致性、可玩性/叙事、技术/兼容性。评分理由记录为审查意见，不是模型通关证明。

## 14. Luna 的阶段化实施路线：一次只把一类做精

### Gate 0：基线冻结与技术 spec（P0）

- 固定当前 HEAD、旧 30 selector 与冻结 seeded 定义／manifest hash；验证 `uv run ruff check .`、`uv run mypy src`、`uv run pytest -q`、`uv lock --check`，留报告；已有不通过则登记，不伪造。
- 写 0017 spec：动作 Schema 升级、scenario 状态隔离、tick 语义、结果与失败终态、公开信息防泄漏、world version 策略、兼容预算门禁、旧 Trace 读写约束。
- 将上述 30 个手工设计条目转换为 30 个 design IDs 和 10 个世界设计卡；具体数值与参考轨迹先做**静态可行性校验**；有矛盾的记录提案，不因为某关尚未实装就无限延期规划。
- **Gate**：旧测试绿、版本不冲突、承诺不碰被冻结的 V2 ledger／holdout，spec 通过审查。

### Gate 1：通用环境契约与三个纵向原型（P0）

挑 **PY-E→PY-M→PY-H（金字塔）** 验证线索和 `submit`；**SU-E→SU-M（地铁）** 验证 `interact`、区段互斥；**AB-E→AB-M（深海）** 验证定量状态变化。它们分别代表推理、离散调度、因果动态，最能证明“不是换皮”。

- 先实现统一的 V3 `ScenarioEnvironment` / Action / Observation 扩展。
- 每个原型先运行 oracle 并通过规则测试，再对照 UI/Trace 可读性做一次人工 walkthrough；只读 UI 不支持新字段时做兼容展示，不把开发 UI 当 Gate 的主要内容。
- **Gate**：至少三个**不同规则**的家族成功跑通并可复盘，任何家族不能靠隐藏 `if scenario_id` 的快速 hack 伪装。

### Gate 2：十家族的 easy 关卡全部精工完成（P0）

建议顺序：PY、SU、AB → SP、LH、PO → VO、JU、LU、CA。目的是让 `logic / schedule / pressure / survival / dynamic navigation / dialogue` 都各自闭环。**每家族一个 easy**，不能某主题先批量复制 easy/medium/hard 模板。

每完成一个家族：先写设计解释→实现状态规则→跑合成轨迹→负例→回放→review→commit。坚持中文叙事文本自然、不重复“这里一片昏暗”和“这里什么都没有”的固定模板。

### Gate 3：medium 层机制组合（P1）

实现 SP-M、LH-M、AB-M、PO-M、PY-M、SU-M、VO-M、JU-M、LU-M、CA-M。重点验证**同一世界的 medium 不是 easy 扩容**。设计审核必须回答：medium 新增的状态变量与因果耦合是什么？新增的策略选择是什么？可观察线索如何让玩家提前判断？

### Gate 4：hard 层“策略困难而非操作困难”（P1）

实现 SP-H、LH-H、AB-H、PO-H、PY-H、SU-H、VO-H、JU-H、LU-H、CA-H。**每一关都先有可执行的参考动作轨迹，再锁关卡定义。**

- 使用穷举/BFS/A*（取决于状态空间）或约束求解检验成功存在；资源时间连续变量必须离散化、状态范围有界；若人工 reference 与模拟器不一致，先定位不一致，按变更流程调整局部值。
- 对硬失败风险给出**为什么失败**的可观察解释；对“错误操作但能恢复”的场景至少有一条合法补救路径；对真正不可恢复的错操作必须在先前有充分警示。

### Gate 5：30 关全套审计、可玩性、冻结与总结（P1）

- `validate_v3_worlds.py` 必须验证 ID 唯一、10 family×3 difficulty、定义/selector 对应、引用实体存在、动作选项合法、双向/单向条件边正确、目标可达。
- `replay_v3_oracles.py` 必须运行 30 条手写参考行为轨迹，在**公共 Action 接口**上获得 30/30 完整成功，且程序每步只以 Observation 作为“脚本行动阶段”的验证依据（不可用 `environment._state` 决定下一步行为）。后置测试代码可以读私有状态验证数值，不可把私有状态作为 Agent 输入。
- 10 个家族分别进行机制独特性审核；每家族一份设计说明，全文不能只是复制替换关键词。至少 10 份“跟踪状态→观察→玩家选择→后果”的机制说明图。
- 人工试玩：每个 easy 关普通玩家可据公开反馈理解，medium/hard 关允许失败但原因可解释；记录“不可知信息、路径软锁、没有真正选择、叙事和规则矛盾”的问题清单并修复。
- 旧世界回归绿，新 Trace schema 兼容旧读者，GitHub CI 全绿；更新 `README`、`docs/scope`、`docs/architecture`、工程日志。README 可在新旧目录选择主题世界与难度，并在 CLI 明示是 Legacy 还是 V3。
- 只需要**手工脚本/单元测试**就可完成这轮验收。真实模型实验和支付预算相关操作需要单独批准；**不得为了追求“30/30模型成功”削弱设计难度或者泄漏规则答案**。

### 14.1 每批 commit / 汇报模版

每批最多围绕一个规则族／基础设施主题提交，不要一次 30 地图巨量提交。提交标题示例：

## 16. 一些必须正视的实际设计风险（Luna 在 spec 阶段确认）

1. **30 关是内容生产＋状态机开发，不是修改 30 个 JSON 就能完成。** 最早的三纵向原型要验证基础架构能正确表达：动态时间、独立资源、对话、推理提交和多种成功条件。
2. **新的动作语义会影响模型兼容性。** 先确保人/脚本能玩通，然后对新 schema 进行离线 Fake/provider mock；在网关稳定前不投入真实请求。Old schema 世界保持老 Action 契约，不让新字段无条件改变旧 prompt hash。
3. **动态关卡的每次 `inspect` 都计时，可能使“调查”变成惩罚。** 因此时间和氧气预算必须容纳合理调查；高难不是猜得到谁最省行动。若 Player 必须一次走对才能活，即使私有 oracle 能通也判定体验不合格。
4. **逻辑谜题可能不唯一或线索冗余。** PY-M 和 PY-H 都应写可计算的枚举约束单测；如某条线索只是气氛文本，应标记 lore，不要假称必要约束。古堡真相必须有事实证据排除其他角色。
5. **地铁是区段调度而非传统房间寻路。** Agent 可以位于 control_room，列车位置放公共 status；不能把列车塞进 `WorldState.current_room` 或要求玩家 `move` 到车所在轨道才能遥控调度。
6. **空间／地图的封闭边很容易产生软锁。** 飞船永久关门、丛林藤门转向、水位封闭路径都必须审计：是否会困住玩家、是否会把关键任务物品锁死、是否公开提示“不可逆”。
7. **参考轨迹不是最短路径证明。** 设计给的是一条候选可行计划，具体 tick、温度、燃料、潮相对齐由代码验证；不要把文件中为呈现思路而给的数字自动写成已证最优步数。
8. **同名“难”跨世界不天然等难**：本次以机制复杂度分档；后续如要做统一 Benchmark，应再使用多模型有限预算试验校准，而非按房间数量硬性归一化。

### V3 结束后再讨论什么？

**只有在世界机制和可玩性真正完成之后**，才决定是否把它们作为“能力组合型 Benchmark”：金字塔→约束推理，地铁→资源调度，古堡→证据归纳，深海／火山→状态预测，月球／极地→有限资源规划，丛林→动态导航，灯塔→时间窗口决策，飞船→风险隔离。届时应该建立横向能力标签和公平的成功标准，而不是继续强化某个已有模型的 150/150 故事。
