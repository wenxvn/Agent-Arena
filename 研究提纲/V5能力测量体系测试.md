## 2. 统一运行时契约

### 2.1 环境接口

建议按仓库风格实现 `reset(map_id, seed, variant) -> observation`、`step(action) -> observation, reward, terminated, truncated, info`，也可适配现有协议，但必须语义等价。

- `action`：带 `type`、`target`、参数的严格结构化对象；地图内允许的动作按自身规格定义。无效 JSON/未知动作与已识别但不满足前置条件的动作区分处理，动作是否耗时**严格遵循该关 V4 规格**。
- `observation`：仅包含当前可见位置、已观察到的事实、允许的公开任务进度、动作反馈；不包含内部真值、完整未来时间线、oracle、seed 到答案映射。
- `info`：区分 public 和 judge-only；普通模型调用和导出的模型可见 trace 永远不能包含 judge-only。裁判统计在隔离评测通道计算。
- `terminated`：成功或硬失败；`truncated`：步数/预算上限；终止后动作必须拒绝且不改变状态。
- 时钟、同 tick 并发、行动耗时、风险结算、资源守恒、窗口端点：逐关按 V4 明确定义，不能强行套统一单 tick 模板。
- `reset` 固定 seed + 固定动作序列产生一致的公开轨迹和裁判状态哈希；相异 seed 的私有差异仅通过合法观察显露。

### 2.2 安全与防泄漏

- 每个地图有独立私有状态对象，不得将 `private_seed_reference`、`answer_table`、`oracle_trace`、`planning/` 路径挂载给模型工具。
- 建立 `public_observation_allowlist`；序列化使用显式字段而不是 `vars(state)`/全量 dataclass dump。
- 自动扫描 prompt、tool message、trace：拒绝含隐藏故障 ID、未来事件 tick、未发现线索、正确答案表、oracle 元数据的字段。
- API Agent 的工具白名单仅含 `observe/act`（及可选 agent-owned memory），不能执行 shell、浏览 repo 或读本地文件；如运行框架无法做到隔离，先修隔离再测试。
- 运行环境确定性、裁判真值固定；API 模型本身可非确定，因此不能将模型输出相同作为 seed 重放的必要条件。

### 2.3 指标与日志

每个 episode 至少记录：`map_id`、设计版本 hash、代码 commit、seed、variant、模型/provider、temperature、context 策略、记忆策略、动作数、环境 tick、成功/失败、失败码、非法动作、重试次数、prompt/completion/cache tokens（可用时）、估算费用及币种、墙钟时间、停止原因。敏感密钥绝不入日志。

Trace 分层：`agent_visible_trace.jsonl`（公开）、`judge_metrics.json`（隔离）、`run_manifest.json`（复现实验配置）。失败分类统一编码：`INVALID_ACTION`、`DEPENDENCY_ERROR`、`WRONG_HYPOTHESIS`、`NO_REPLAN`、`MEMORY_LOSS`、`REPEATED_ACTION`、`RESOURCE_EXHAUSTION`、`TIMEOUT`、`UNSUPPORTED_CLAIM`、`SAFETY_VIOLATION`、`PROVIDER_ERROR`；不能单凭结果臆断原因，分类需有轨迹证据。

## 3. 六图逐关实现与测量协议

### MAP-08｜看不见的裂缝：主动诊断 / 信息增益

**严格实现**：六舱环、X/Y 测试站、候选漏点 B/D/F、初始观测等价、测试签名、测试耗时、水位上升、唯一密封剂、错误修复不可重试、恰好水位边界；以该关设计 YAML 为唯一数值来源。

**必须测试**：三种隐藏真值初始公开 Observation 完全一致；X/Y 各自按真值返回正确签名；重复测试无新信息；测试/移动逐 tick 结算水位；水位 `==7.0` 与 `>7.0`；修错终止；修对成功；不同先验的决策评价不能硬编码首选 X。

**能力对照**：A 完整信息采集工具；B 禁用压力测试的随机猜测基线；C 允许测试但不给 Agent 外部假设记录；D 提供结构化假设表。对照组保持动作成本和任务定义不变；若禁用测试造成可解性改变，明确标注为**机会基线**而非纯粹能力消融。

**主指标**：诊断准确率、错误修复率、测试数量、有效信息增益、任务成功率；按 B/D/F 分层。**解释警戒**：高成功率不自动等于善于信息增益优化，需检查首测和停止时机。

### MAP-16｜单线会车：约束调度 / 死锁避免

**严格实现**：A—X—M—Y—B 与 M—D 侧线；同步预约、原子结算、区段互斥、泊位容量、相向交换、同 tick 交班、取消预约、死锁判定。预约动作不推进世界 tick，`move_train` 才结算；不得误套普通步进。

**必须测试**：两套六 tick 手工成功调度；BFS/穷举最短 makespan=6 的独立验证；冲突三类与真死锁；同 tick D→M 与 M→X 合法交班；冲突时位置、能耗、tick 不改变；不得将所有停顿判成死锁。

**能力对照**：A 直接 ReAct；B 提供可读的公开约束表；C 提供外部计划草稿工具但不提供最优动作；D 无规划草稿。**主指标**：成功率、makespan、相对最优差距、冲突数、死锁率、预约修正次数。**警戒**：该图状态小，可能被穷举策略轻易解决，应作为调度正确性与算法基线，不直接代表复杂长期规划。

### MAP-18｜故障传播：动态重规划

**严格实现**：三条线路、六车、18 名乘客、站台容量、R2-R3 在 t5–t9 封闭、t10 恢复、t4 非定位告警、共享段同步移动与折返/取消约束。无告警和告警组的隐藏故障 seed、起始状态一致。

**必须测试**：t0–t3 两组公开状态一致；t4 告警不泄露故障区段/时长；t5 关闭、t9 仍关闭、t10 恢复；合法无故障排班；两条手写恢复策略；70% 服务阈值；同 tick 容量/闭塞；有无告警的配对延误差应按设计记录验证（纸面为 3 passenger-ticks，不应直接硬编码为评分常量）。

**能力对照**：A 完整观察 + 允许重规划；B 相同观察但固定初始计划不调整（诊断性基线）；C 告警开/关配对；D 结构化计划监控开/关。**主指标**：服务率、乘客延误、故障后首个有效调整所需 tick、无效旧计划动作、恢复时间、安全违例。

### MAP-22｜没有地图的森林：空间记忆

**严格实现**：12 节点、15 条边、当前地点路标和出口方位可见、邻居身份未知、实际走边后才能记端点、记忆最多 32 条、返回营地目标切换、30 步界限。禁止 Observation 自动输出完整地图、全局访问历史或推荐回程路线。

**必须测试**：拓扑连通、最短 A→L 为 4、往返理论 8、18 步图记忆巡回、30 步 DFS 边界成功；相似三叉路标可通过局部特征区分；未走边不可记录；记忆写入不会预知邻接；30/31 步端点。

**能力对照**：A 完整历史；B 最近 5 步历史；C 短历史 + 32 条结构化地图记忆；D 固定罗盘贪心仅作为**特定策略基线**，不得称为所有无记忆 Agent 的理论表现。再增加“固定相同探索轨迹后仅比较返程”实验，以剥离探索效率和记忆质量。

**主指标**：目标发现率、返营成功率、路线回溯正确率、独立边识别、重复访问、相同已知拓扑下的返程超额步数。**警戒**：探索好不代表记忆好，必须单独报告。

### MAP-26｜失败的维修计划：错误反馈与自我纠错

**严格实现**：T—D—A—B 四节点、三种隐藏故障、固定粗日志、三种 typed 测试、两枚备件、错误替换反馈、回滚、同类重试成本、成功时的备件保留要求；具体胜负边界依设计文件，不得为了简化删除。

**必须测试**：三 seed 初始观测相同；各测试对不同故障给固定一致读数；正确/错误替换反馈不同但不泄露未测试真值；重复错误成本递增；备件耗尽与最后一枚正确维修但不满足保留要求；终止顺序和重放。

**两条测量轨道，必须分开报告**：
1. **自由诊断轨道**：Agent 从初态自行诊断维修；主测主动诊断和资源谨慎性，不宣称专测自我纠错。
2. **标准化失败后恢复轨道**：所有 Agent 获得**同一合法可达失败前缀所产生的公开历史与当前环境状态**，包括一次合理但错误的替换及其反馈；从这一状态继续行动。前缀必须经环境真实回放得到，不能拼接虚构状态，也不能耗尽剩余成功所需备件。对比完整反馈、隐藏错误反馈、结构化错误摘要等条件；若隐藏反馈使任务不可辨识，明确标注为信息剥夺对照。

**主指标**：反馈后首次有效假设修正、重复同类错误率、恢复成功率、恢复动作/备件成本。**警戒**：自由轨道无错误通关不能证明有纠错能力。

### MAP-30｜午夜审判：长间隔证据记忆 / 证据一致性

**严格实现**：古堡一层/二层与密道拓扑、三事件时间线、早期 Q4 暗码身份映射、固定证词触发条件、物证/证词独立来源、不可逆指控与单次错误容忍（如原设计有）、40 tick 截止；不得让 NPC 自由生成可改变真相的证词。

**必须测试**：所有证据仅在合法访问后公开；条件证词在展示相应上游证据前后有确定差异；相同条件重复问答一致；Q4 身份映射不从未访问的档案泄漏；三条 25/32/34 tick 参考成功轨迹；过早指控、无依据指控、错误身份、40/41 tick 边界。

**能力对照**：A 完整历史；B 最近 5 步；C 最近 5 步 + 四格结构化案卷。增加“相同已发现证据、不同历史保留方式”的固定调查前缀，专门测证据召回；另测证据是否足够时的提交谨慎性。

**主指标**：Q4 长间隔正确引用、三事件证据完整度、时间线一致率、过早指控率、无依据断言、成功率。**警戒**：推理错误与记忆丢失须通过轨迹证据区分。

## 4. 离线验证门槛：API 前必须全绿

1. **设计一致性**：六关拓扑、动作成本、初态、胜负条件与 V4 对齐；不一致处有 DCR 和更新后的 Oracle。
2. **Oracle 真回放**：每条手写成功轨迹在**真实 V4 环境**重放成功，逐动作公开观察与预期对齐；绝不只校验文件格式或匹配最终答案。
3. **失败轨迹**：每关至少三种独立失败机制实际触发，失败码和发生时刻一致；失败后不可继续改变状态。
4. **边界测试**：截止 tick 包含端点、资源恰好耗尽、相向交换、同步结算、重复工具调用、未知动作、缺失参数。
5. **确定性**：固定 seed + 固定动作序列至少重放两次，公开 trace 与裁判状态 hash 一致；不同 seed 只在预定私有事实不同。
6. **无泄漏**：黑盒模型工具无法访问 repo 文件；初态/未探索阶段公开字段白名单通过；自动检查 oracle、隐藏真值、未来事件不在 agent-visible trace。
7. **独立求解器**：MAP-16 用 BFS 校验最优 6 tick；MAP-08 枚举诊断结果与信息增益；MAP-18 核对无故障可行时刻表；MAP-22 验证图论最短路径；MAP-26 枚举剩余备件可恢复性；MAP-30 验证证据依赖图可达。求解器不能共享与环境完全相同的状态转移核心后自称独立验证。
8. **回归**：项目现有 pytest、lint/type-check（按仓库实际工具）全通过；记录命令、版本、数量、失败原因，不得凭设计文档写“通过”。

未全绿：停止真实 API 调用，输出阻塞清单。允许逐关继续离线修复。

## 5. API 接入与成本控制

### 5.1 CLI 与配置

提供类似命令（实际参数按现有 CLI 约定调整，并在 README 给出准确可复制命令）：

```bash
# 无付费调用：检查环境、提示词、动作解析和 mock provider
uv run python scripts/v5_pilot.py --maps 08,16,18,22,26,30 --provider fake --dry-run

# 显式启用真实模型：仅在离线全绿、密钥已配置、预算已批准后
uv run python scripts/v5_pilot.py --maps 08,16,18,22,26,30 \
  --provider <configured-provider> --model <model-id> \
  --seeds 0 --episodes-per-map 1 --max-total-cost-usd 2 \
  --max-actions-per-episode 150 --max-output-tokens-per-call 1024 \
  --execute-paid
```

上面 `--max-total-cost-usd 2` **仅是示例硬上限，不代表实际预计花费或用户已批准预算**；具体价格和模型支持需读取 provider 实际配置。未提供 `--execute-paid` 一律不调用付费 API。若 provider 无法报告精确 usage，使用保守估算并在预算不可保证时停止。

必须支持每局与全局双重限制：最大动作数、最大模型轮数、最大输入/输出 tokens、最大美元预算、墙钟超时、连续错误上限。HTTP 429/5xx 使用有限退避；重试不重复执行已成功的环境动作；请求幂等和断点续跑需记录。不得记录 API key。

### 5.2 分阶段实验

**Stage A：离线 dry-run**：六图 × fake provider，检查协议和动作链，不声称测出模型能力。

**Stage B：真实 API 冒烟**：先单一模型，六图每图 1 局、seed0；只检查协议、循环、成功/失败原因、平均 token 与成本。若出现系统性接口失败，立即停机修复。

**Stage C：最小能力对照**：每图先选择 2–3 个**能直接回答研究问题**的条件，优先相同 seed 配对；每条件先做少量局验证指标是否变化。不同随机 seed 的数量由预算和实际方差决定，不预先做 10×3×5 的矩阵。API 温度/系统提示/工具集合/最大预算尽量固定，改变变量必须单独记录。

**Stage D：扩大验证（须另行明确批准预算）**：对显示出测量敏感性的地图再扩充 seed、模型和重复运行；报告 Wilson 区间或适合样本规模的区间，样本太小时明确标注探索性结果，不能据 1–3 局排名模型。

## 6. 评测与归因分析

- 输出每关原始成功率、资源/时间成本、专属指标、失败类型与每个对照的配对差异；不要只给总分。
- 总分可作为辅助展示，但六种能力的权重必须公开；不可用总分替代能力雷达图和逐关数据。
- 控制混淆因素：相同 provider、model、temperature、token/action budget、提示词格式、地图 seed；记忆对照须说明是否改变有效上下文长度与额外 token 开销。
- **验证性标准**：对照机制确实改变 Agent 可用的信息或策略；指标能检测这种变化；观察泄漏为零；至少存在可解释的成功/失败差异或合理的无差异结论。不得强迫产生显著差异。
- **效度边界**：一张图的结果不能直接推广为某模型通用的“记忆能力分数”；尤其 MAP-08 的诊断、MAP-26 的纠错、MAP-22 的探索/记忆需要拆分报告。
- 公开基准与保留测试分离：固定手工地图适合回归；未来正式泛化评估需要同机制、不同实例的人工审核 holdout，不能仅靠改名或重排节点。

## 8. 执行顺序与检查点

**P0 审计与设计修正**：核对六图文件和接口；解决 MAP-26 标准化失败前缀的可恢复性、MAP-22 记忆与探索混淆、MAP-30 证据依赖等。产出差异报告。

**P1 统一 V4 contract**：先完成 reset/step、可见性边界、日志、预算、假 provider；单元测试通过。

**P2 最小环境逐关实现**：推荐 16→08→22→26→18→30；每实现一关立即跑该关成功/失败/边界/泄漏测试，再继续下一关。禁止六关批量复制同一玩法模板。

**P3 独立审计**：六关所有离线验收通过；完成 V3 回归；记录真实命令与测试输出。

**P4 API 冒烟**：仅在可用 provider、用户授权的预算和明确执行许可满足时启用；否则保留 dry-run 报告和一条可复制的真实运行命令，不虚构模型成绩。

**P5 能力对照与总结**：完成可负担的小规模配对实验，生成逐关报告和失败案例；决定哪几关真正具有可测量敏感性，提出其余 24 关的接入门槛。

每阶段结束更新 `docs/v5/README.md`：完成项、证据、未完成项、下一步。遇到设计冲突先停该关并记录，其他独立地图可继续，不得以“赶进度”为由跳过验证。

## 10. 给 Luna 的最终交付格式

最终回复必须按顺序提供：
1. 实际 Git HEAD、修改文件列表、关键架构说明。
2. 六张地图逐关状态：`DESIGN_REVIEWED` / `RUNTIME_IMPLEMENTED` / `OFFLINE_VERIFIED` / `API_SMOKE_TESTED` / `CAPABILITY_PILOTED`，不得越级宣称。
3. 实际执行的命令、测试通过数/失败数、未解决问题与 DCR。
4. API 是否真实调用、调用模型、局数、token、费用；未调用必须明确写“未运行真实 API”。
5. 逐图能力结论与证据，指出未测出的能力或设计混淆。
6. 后续 24 图建议与是否具备扩展条件。

**最终成功定义**：六图在可运行、无泄漏、确定性、可回放的环境中能够接受真实 Agent 操作，并具备成本可控、可以回答明确能力假设的测试协议；不是简单的“六图跑通”或“模型成功率高”。
